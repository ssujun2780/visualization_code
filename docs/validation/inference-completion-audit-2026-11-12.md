- 읽은 계약: `presentation.md`, `inference-model.md`, `structure-presentation-policy.md` 적용 규칙 1–6, `structure-composition.md` RC-01–08, `structure-extensions.md` EXT-01–07, 배열/연결/트리/BST/그래프/연관 조회/문자열 경로/PPR 관련 명세. 실행 관계 API는 분리 경계와 입력 연결 부분을 확인했습니다.

| H | 문서가 완료 범위를 서로 다르게 서술함. 공통 완료표와 현재 지원/미지원/미검증 상태 정리 | `structure-composition`, 개별 명세, validation 기록 | 조항→공개 API→생성기→조회/추천→검증 연결. 고친 항목을 미구현으로 다시 세거나 초안을 구현 완료로 세지 않음 | 2–4시간 |

**합계: 현재 확인한 범위를 마무리하는 계획치 54–106시간, 하루 8시간 환산 약 7–14일입니다.** 새 결함이 없다는 보장은 아니며 G의 측정 결과에 따라 조정해야 합니다. ‘두세 개 수정 후 완료’로 잡을 근거는 없습니다. 순수 자동 대기시간 또는 앞으로 이 채팅을 계속 열어 둘 시간으로 해석하면 안 됩니다.

순서는 **E → A·B → C → D·F**이며 G·H를 각 묶음에 함께 적용하는 편이 중복 작업을 줄입니다. 이미 통과한 예제를 매번 전부 다시 실행하지 않고, 공통 계약을 건드리는 경로와 표현 변형·반례를 묶어 검사합니다. 전체 통합 회귀는 별도 승인 없이 자동 반복하지 않습니다.

## 코드에서 확인한 원인과 수정 방향

### A·B: 값 출처와 비교 의미

- `linked-views.mjs`의 루트 정적 연결은 직접 호출 인자·선언 별칭을 따라가고, 함수 반환 등 미지원 표현에서 명시적으로 멈춥니다. 반환으로 루트를 받는 정상 구현 전체를 동일하게 다룬다는 근거가 없습니다.
- `index-relations.mjs`의 AST 인덱스 수집과 `priority-comparison.mjs`의 포인터 필드 비교 복원은 별도입니다. 비교 정책 발견과 힙의 부모/자식·활성 범위 발견을 연결해야 합니다. 알려진 비교 정책만으로 힙 노드를 추측해 만들면 안 됩니다.
- `associative-views.mjs`는 CALC의 `==/!=` 정수 READ에서 키를 찾습니다. strcmp 반환과 버킷 키 출처를 같은 동등 판정으로 소비하지 못합니다. 버킷 접근은 같은 activation 조건도 있으므로 실제 인자/반환의 출처 경로로 확장해야 합니다.
- `storage-semantics.mjs`의 `num()`은 `Number.isSafeInteger`만 허용합니다. 이를 공유하는 확장 관계의 숫자 영역을 BST의 BigInt와 동일하다고 주장할 수 없습니다. 정수 좌표와 payload/키 수치를 분리해야 하며, 주소·인덱스를 실수로 느슨하게 처리하면 안 됩니다.
- 동적/지역 배열의 작은 포인터 비교 두 건은 후보 미생성까지만 확인했습니다. 앞서 성공한 힙 속 비교와 어떤 근거 차이 때문에 갈리는지 추가 분리 검사가 필요합니다. 지금 수명 버그로 단정하지 않습니다.

### C: 동작을 나타내는 필수 사실과 우연한 구현 모양

```c
/* 정상적인 XOR 지연 갱신 */
void apply(int k, int n, int delta) {
    if (n % 2) value[k] ^= delta;
    tag[k] ^= delta;
}
```

`composed-update-views.mjs`는 같은 activation·인덱스 출처를 공유하는 집계 WRITE와 태그 WRITE를 먼저 짝지어야 application을 만듭니다. 짝수 구간에는 집계 WRITE가 없으므로 부모 application과 전파가 빠집니다. 이를 고칠 때 가상의 집계 WRITE를 추가하면 안 됩니다. 태그의 실제 버전·구간·전달·해제 근거를 독립적으로 연결해야 합니다.

상수 잎은 `range-aggregate-views.mjs`의 외부 배열 READ에서 좌표를 얻는 경로에 들어가지 못합니다. 실제 자식 관계로 얻은 논리 좌표와 원본 데이터의 저장 출처를 별개로 표현해야 합니다. full 플래그 큐도 저장 배열·커서 인식만으로 논리 길이를 결정할 수 없으며 분기·상태 전환 근거가 필요합니다.

### D: 전용 기능이 있어도 사용자 선택까지 연결되지 않음

`structure-conditions.mjs`의 공통 정의는 11개이고 그래프·사슬·트리·BST·AVL/RB 중심입니다. `structure-relations.mjs`도 linked/rooted-index/pointer-tree/sequence 후보만 투영합니다. `structure-presentation.mjs`의 `expectedFor()`는 heap·segment-tree·disjoint-set 등에 기본 기대 조건을 연결하지 않습니다. `conditionBindings`의 명시 역할은 color/height뿐입니다.

이미 존재하는 힙/DSU/구간/트라이 전용 검사기를 버릴 이유는 없습니다. 저장 표현 어댑터와 조건 검사를 연결하고, 사용자에게 필요한 최소 역할 지정이 같은 API로 들어오게 해야 합니다. 임의 custom 식별자를 저장하는 기능과 임의 자료구조의 역할을 실제로 연결하는 기능은 구분해야 합니다. 사용자 정의 렌더러나 규칙을 자동 생성하는 기능은 기존 문서에도 약속되어 있지 않습니다.

### E: 기록 한도 자체보다 조회의 정직성이 문제

`sequence-lookup-views.mjs`는 한도 도달 시 마지막 슬롯을 최신 상태로 바꾸고 그 상태에만 historyGap을 붙입니다. 중간 시점 조회는 생략 직전의 정상 상태를 반환합니다. coverage에 omittedStates/생략 구간도 없어서 공통 관계 조회가 이 틈을 검출하지 못합니다. 새 코드의 x54→x51 결과가 이 경로입니다.

해시 이력에도 비슷한 마지막 슬롯 교체 방식이 있습니다. 이는 **코드상 동일 위험**이며 이번에 별도 해시 재현까지 한 것은 아닙니다. 복합 우선순위는 비교 반환·인덱스 트리 상태를 체크포인트로 쓰며 별도 수명 체크포인트가 없어 추가 검증 대상입니다. `record-evidence`의 64단계/8192개 출처 탐색 한도는 null/빈 배열로 돌아가므로 근거 없음과 예산 초과를 구분하는 진단도 필요합니다. 사용자 합의대로 기록 한도를 무제한으로 늘리는 작업은 요구하지 않습니다.

### F: 여러 기본 관계의 조합

현재 `partitionSelectionStructures()`는 정수 대표 후보만 소비합니다. 포인터 대표 후보도 있어야 같은 선택 관계가 구성됩니다. 단순 이름별 알고리즘 분류기를 추가하는 방향은 필요하지 않습니다. 연결·순서·소속·키·구간·공유·부가 상태를 조합하고 각각의 근거를 제공하는 기존 목표를 유지합니다.

비트 연산은 `packedAccesses`라는 관찰 근거가 있으나 이를 임의의 논리 집합/간선 소속으로 자동 복원하는 계약은 없습니다. 미방문 간선·고립 정점과 탐색 완료의 의미도 관측 여부와 구분해야 합니다. BFS/DFS/다익스트라/Kruskal이라는 이름만 붙여 방문 완료·최적성을 확정하는 기능으로 대체하지 않습니다. 필요한 경우 사용자 역할 연결로 보완할 수 있어야 합니다.

실행 관계 추론기는 별도 모듈입니다. 현재 실제 `scripts/execution-relations/v2/` 구현이 있으므로 문서의 초안 표기만 보고 전부 미구현으로 세지 않았습니다. 소비부는 `storageBindings` 또는 시간 정보가 있는 최상위 nodes를 사용하지만 많은 자료구조 후보는 states 안에 노드가 있습니다. 이 시점별 대응을 전달하는 어댑터의 통합 검증은 남아 있습니다. 해당 모듈과 UI는 이번에 변경하지 않았습니다.

### G·H: 검사와 완료 범위

`tests/ir-priority-partition-range.test.js`의 run 보조 함수는 expected 파일을 현재 소스로 다시 쓰지만 cached=true이면 기존 execution JSON을 읽으며 그 실행이 같은 소스에서 나왔는지 비교하지 않습니다. 파일명 변경·소스 변경 후 stdout이 같으면 다른 실행 기록으로 검사할 가능성이 있습니다. 실제 stale cache가 발생했다고 확정한 것은 아닙니다. 현재 소스/도구 버전/옵션과 캐시를 묶고, 기대값은 실행 전에 별도로 고정해야 합니다.

기존 검증기가 저장 범위·사건 출처·구성원·전파 버전을 검사하는 부분은 유지합니다. 다만 생성기와 검증기가 같은 제한된 출처 함수/배치 함수를 공유하면 누락을 함께 놓칠 수 있습니다. 독립적인 소스 기대 관계와 식별자·순서·종료·시점 검사를 추가해야 합니다. 이번 재현처럼 ‘stdout 정상, inference.status=completed’만으로 추론 정확성을 판단할 수 없습니다.

문서 불일치의 실제 예:

- 표현 정책은 복합 키를 검사 불가라고 적지만 BST 명세/실제 코드는 복합 정수 키를 구현했습니다.
- 트리 문서는 색 역할 자동 추론 미구현으로 서술하지만 EXT-03은 색 **후보**를 구현했습니다. 빨강/검정 의미 자동 확정과 구별해 고쳐야 합니다.
- 그래프 문서는 DSU와 선택 간선의 합성 전체를 미구현으로 적지만 정수 대표+레코드 복사 경로는 구현돼 있습니다.
- PPR의 ‘자기 대표 포인터/가산 태그’ 설명은 최신 NULL/센티널 및 곱셈/XOR/OR 지원 범위와 어긋납니다.
- RC-08은 ‘12계열’을 언급하나 해당 절에 완료 범위를 구성하는 12개 항목표가 없습니다. 숫자만으로 완료 분모를 정할 수 없습니다. 위 구현 경로와 원래 사용자 목표를 잇는 명시적 완료표가 필요합니다.
- 과거 `structure-inference-next.md`의 이미 수정된 문제를 현 잔여 결함으로 다시 세지 않았습니다.

## 마무리 기준과 남는 불확실성

각 기본 관계가 저장 표현 변형을 통과하고, 같은 근거가 시점 조회·추천·사용자 지정·조건 검사까지 이어져야 합니다. 모순/관측 부족/한도/미지원은 서로 구별되고, 사용자 지정이 추론 오인식을 교정할 실제 역할 연결을 제공해야 합니다. 검증은 특정 이름·상수·예상 정답에 대한 분기가 아닌 공통 계약으로 수행해야 합니다.

임의 프로그램의 의도를 완전히 알아내거나 실행하지 않은 모든 경로의 자료구조 조건을 증명하는 것은 현재 근거로 보장할 수 없습니다. 이것을 이유로 문자열 키, full 플래그, 태그 전파 같은 일반적인 구현을 목표에서 빼지는 않습니다. 반대로 모든 파생 자료구조 이름마다 전용 분류기를 새로 만들겠다는 목표로 늘리지도 않습니다.

화면 배치·가독성·애니메이션 검증은 별도 작업이며 이번 API 감사로 완료되지 않습니다. 알려진 누락을 위 8개 묶음으로 마무리하고 공통 완료표를 통과했을 때 추론기 완료 판단을 다시 내릴 수 있습니다. 이번 보고서는 수정 완료 보고가 아닙니다.
