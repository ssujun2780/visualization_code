## No12: 검사 수정과 실제 모델 수정의 구분

기존 검사는 마지막 frame.end가 닫는 중괄호인 18행을 가리킨다고 가정했습니다. 수정 전 모델도 실제 `return 0`인 17행을 가리켰으므로, No12 자체는 오래된 검사 기준이었습니다.

기대값을 18에서 17로만 바꾸지 않았습니다. 같은 활성화의 FLOW/return과 SPACE/frame.end가 **같은 sourceNodeId**를 가리키는지 검사하고, 서로 다른 조기 반환문을 실행하는 사례도 추가 확인했습니다.

그 결과 `if(n) return a[1]+n; return a[0];`에서 앞 반환문을 실행해도 정리 사건이 뒤 반환문에 연결되는 실제 누락을 발견했습니다. LLVM의 공용 ret 블록에 대해 기존 모델은 반환구 WRITE와 FLOW만 실제 반환 사이트로 연결했습니다. 동일한 기록된 반환 저장소 근거를 SPACE 정리 역할에도 적용했습니다. 검사를 약하게 바꾸지 않고 실패를 재현한 뒤 모델의 공통 역할 연결을 수정했습니다.

## 준비 성능

이번 작업 직전 모듈 복사본과 수정 후 모듈에 같은 고정 실행·추론 기록을 넣었습니다. 별도 Node 프로세스에서 전후를 번갈아 직렬 측정했습니다. 32노드는 각각 3회 중앙값이며, 8·16노드는 각각 1회 측정입니다.

| 리스트 규모 | 준비 시간 전→후 | 최고 RSS 전→후 | 전체 준비 JSON |
| ---: | ---: | ---: | --- |
| 8 | 123.01→101.10ms | 130.87→116.10MiB | 해시 동일 |
| 16 | 620.73→545.34ms | 180.61→169.28MiB | 해시 동일 |
| 32 | 5,267.34→3,313.30ms | 287.34→286.11MiB | 해시 동일 |

32노드 준비 시간은 약 **37.1% 감소**했습니다. 이전 보고서의 단일 측정과 다른 시점에 비교한 값이며, 이번 전후 중앙값끼리 비교해야 합니다. RSS는 입력·직렬화 등을 포함한 프로세스 최고치로 브라우저 메모리가 아닙니다. 메모리 개선이 크다고 주장하지 않습니다.

32노드의 펼친 결과는 15,250,356바이트, 공유 전달 형식은 2,032,049바이트로 전후 같습니다. 최종 그래프로 과거 상태를 대체하거나 준비 항목을 삭제하지 않았습니다.

## 추론 한도: 제한 제거와 제한 처리 완료는 다릅니다

버블32는 정상적인 19,351개 실행 사건에서 배열 관리 후보 상태 2,987개를 만듭니다. 기본 maxStates=2048에서는 939개가 생략되어 partial입니다. 새 진단은 다음 정보를 함께 제공합니다.

```json
{
  "limit": 2048,
  "retainedStates": 2048,
  "omitted": 939,
  "historyGapFromExecutionId": "x12123",
  "historyGapToExecutionId": "x19351"
}
```

생략 구간은 `[x12123, x19351)`이며 최신 보관 상태 x19351 자체는 생략된 상태가 아닙니다. 같은 원본 기록에 명시적으로 `limits: {maxStates:4096}`을 전달하면 2,987개 상태를 보관하고 completed가 됩니다. 원본 기록 해시는 같고, 기본 분석에 남은 모든 상태가 전체 분석의 같은 사건 상태와 정확히 일치했습니다. C를 재실행하지 않았습니다.

모든 입력에 무한 기록을 허용한 것이 아닙니다. 기본 상한을 올리거나 partial을 숨기지 않았으며, 한도 발생·조회·재분석 복원의 동작을 확인한 것입니다.
