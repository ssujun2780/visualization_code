## 코드에서 먼저 정한 예상

- `(key % 10)` 오름차순, 동점의 tie 내림차순: 키 14/22/32/43, tie 1/5/9/2에서 루트 tie는 9입니다. 나머지 키는 4/2/2/3이며 루트 key를 19로 바꾸면 힙 조건 위반입니다. 구조체 필드 순서를 바꾸고 값으로 전달해도 같은 결과여야 합니다.
- `(key*2+tie)%7`: 키 14/22/27/43와 같은 tie에서 결과는 1/0/0/4, 루트 tie는 9입니다. 루트 key를 21로 바꾸면 위반입니다. 원래 key의 단순 순서로 대신하지 않습니다.
- `strncmp(...,2)`는 두 글자 또는 먼저 만난 NUL까지만, `memcmp(...,3)`는 NUL을 포함한 세 바이트를 비교합니다. 같은 바이트 값이 있어도 읽은 필드·범위·비교 길이가 다르면 다른 키입니다.
- 구간 합 10에 `(2,3)`, `(3,1)`을 적용하면 태그는 `(6,10)`, 합은 100입니다. 부모 태그를 모두 전파하면 자식 합은 38/62, 부모 태그는 1/0입니다. 같은 `(2,3)`을 두 번 호출하면 `(4,9)`, 합 76, 자식 합 30/46입니다.
- 자식 사이에서 부모 곱셈 태그가 바뀐 코드의 실제 출력은 `100 38 69 1 0`입니다. 정상 종료해도 같은 부모 버전을 완전히 전파한 근거는 아닙니다.
- 색 코드 23/17과 5/99 모두 연동 변경과 루트 복구를 관측해야 제안합니다. 이후 루트를 빨강으로 바꾼 상태는 같은 해석으로 위반을 표시해야 합니다. 루트 복구가 없으면 미확정입니다.

새 입력과 stdout 예상은 실행 호출 전에 `.c`와 `.expected.json`으로 저장하며, 구성원·연산·순서 기대는 테스트 코드에 명시했습니다. 자료구조를 완성하도록 원본 C 값을 보정하지 않았습니다.

## 검사에서 발견해 수정한 공통 문제

1. **비교 길이의 암시적 변환:** 상수 2가 size_t 변환 CALC를 거친다는 이유로 동적 길이로 분류됐습니다. 실제 의존 입력이 없는 상수 접힘만 통과시켰습니다. 변수에서 얻은 관측 숫자를 상수로 취급하지 않습니다.
2. **문자 배열 필드의 복사 출처:** 필드에 memcpy한 뒤 원본 바이트 배열까지 거슬러 올라가며 현재 레코드 필드 신원을 잃었습니다. 실제 읽은 필드 신원과 바이트 복사 근거를 구분했습니다. 구조체 인자 복사 추적은 유지합니다.
3. **제한된 이력의 구간 근거:** 표시 상태와 proofStates의 순서를 섞어 구간 레이아웃을 잘못 선택했습니다. 실제 사건 순서의 검증 이력을 사용합니다. 생략 구간을 화면용 정상 상태로 채우지 않습니다.
4. **함수 내부 포인터의 루트 오인식:** FLOW/enter에 없는 functionId를 읽어 내부 임시 포인터를 외부 루트로 포함했습니다. 실제 호출 프레임의 함수 식별자로 판별합니다. 숫자 키 상태는 관련 레코드·루트·정책·관계 변화 때 갱신하며, 외부 문자열 메모리 변경 감시는 유지합니다. 수명 조회는 객체 ID 색인을 사용합니다.
5. **복합 태그의 반복 호출/버전:** 같은 입력 출처를 공유하는 여러 호출의 쓰기가 섞일 수 있었습니다. 실제 호출 계보와 쓰기 버전, 중간 덮어쓰기를 함께 확인합니다. 더 좁은 갱신 호출이 입증된 경우 바깥 호출의 교차 조합을 제외하고, 경쟁 조합이 남으면 확정하지 않습니다. 각 자식은 같은 부모 태그 쓰기에서 값을 받아야 합니다.
6. **계약 검증 진단 순서:** 추가한 정책 전체 일치 검사가 구체적인 반환 소비·복사 범위 오류보다 먼저 발생했습니다. 구체 출처 검사 후 전체 정책 검사를 수행하도록 옮겼습니다. 기존 검사와 전체 정책 검사를 모두 유지했습니다.

## 검사 코드의 정정·확대

- 기존 `parity-priority` 검사는 `%`를 미지원으로 보고 후보 0개를 요구했습니다. 이번 EXT-07 구현 이후에는 코드의 **짝홀수 오름차순 → 원래 키 오름차순 → tie 내림차순**, 변환 식 `% 2`, 실제 루트 `[0,2,9]`를 검사합니다. 미지원 검사를 무조건 삭제하지 않고, 양쪽 레코드를 섞은 조건 `((x.a+y.a)&1) ? ... : ...`을 별도 반례로 검사했습니다. 원래 stdout 기대는 유지했습니다.
- 값 인자 예제는 필드 선언 순서가 달라 첫 번째 저장 성분을 첫 번째 비교 키로 착각했습니다. `keyOrder`의 성분 ID로 검사 대상을 찾도록 정정했습니다. 키 값·방향 기대는 그대로입니다.
- 새 색 검사에서 내부 status의 `violated`와 공개 assessment의 `contradicted`를 혼동했습니다. 기존 RC-05의 공개 이름으로 고쳤으며 실제 `red-black-root-color` 경고, 사용자 지정, 의미 유지까지 검사합니다.
- 추가 변환 키/NUL 입력 두 개는 비교 분기가 전부 관측되지 않았는데 완전한 정책을 기대했습니다. 해당 입력은 **미확정 반례로 그대로 보존**했고, 모든 필요한 방향을 실제로 실행하는 별도 입력을 만들어 정상·위반 판정을 검사했습니다. 추론 결과를 보고 미실행 분기를 채우지 않았습니다.
- 32개 규모 검사에서는 기존 관계·이력 예산에 따른 `partial`을 구분합니다. 선택한 힙의 **32개 구성원, 31개 간선, 정상→위반, 생략 상태 0개**는 계속 강제합니다. `partial`이라고 구성원 누락이나 변환 실패를 허용하지 않습니다.

## 남은 경계
