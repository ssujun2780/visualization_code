# No8: 610개와 641개의 실제 사건 비교

결론: **사건 수 고정 검사가 이후의 중간언어 계약 변경을 반영하지 못했습니다.** 증가한 31개는 삼항 선택 FLOW 30개와 상수 부호 연산 CALC 1개입니다. 이 증가분에서 중복 실행·값 전달 오류는 확인되지 않았습니다. 검사나 모델은 수정하지 않았습니다.

## 비교 자료와 방법

- 과거: `test-results/no8-source-process-2026-11-02/{plan,trace,observations.plan,observations.trace}.json` — 610개.
- 현재: 같은 No8.c를 `traceModel(..., {inference:false, includeObservations:true})`로 새로 실행 — 641개.
- 원본 C는 LF/CRLF 차이만 있습니다. 줄바꿈 정규화 후 완전히 동일합니다.
- 비교 과정에서 사건 ID 변경과 C 자료형 메타데이터 보강을 실행 내용 변화로 오인하지 않도록, 소스 행·작업 종류·연산자·객체·접근 범위·실제 값·호출 인자·출력·정리 대상을 대응시켰습니다. 순서 차이는 따로 검출하고 원시 관찰과 대조했습니다.
- 모델·계측·검사·No8 소스 212개 파일은 점검 전후 해시가 동일합니다. 생성한 파일은 이번 점검용 기록과 이 문서뿐입니다.

### 삼항식: 비교와 선택을 구분한 30개

설명용으로 반복 변수 이름을 i로 줄였습니다.

```c
printf("%d%c", array[i], i == 4 ? '\n' : ' ');
```

이 형태가 9·13·24·34·38·42행에 있으며 각각 5회 실행됩니다. 따라서 선택은 정확히 6×5=30번입니다. `i==4` 비교 CALC는 과거와 현재 모두 30개입니다. 비교 계산을 두 번 수행한 것이 아닙니다.

9행의 첫 반복:

```text
과거: x19 CALC == → 0
      x20 FLOW call printf(3, 32)
      x21 WRITE output "3 "

현재: x19 CALC == → 0
      x20 FLOW conditional: 조건 0, false 가지 선택, 결과 32
      x21 FLOW call printf(3, 32)
      x22 WRITE output "3 "
```

과거에는 선택 정보가 호출의 `inputEvaluations`에만 있었습니다. 현재는 선택 작업 자체가 FLOW 사건으로 나타납니다. 조건 CALC → 선택 FLOW → 호출 순서를 확인했고, 호출의 `controlInputs`에도 선택 사건이 연결됩니다. 선택된 문자는 리터럴이므로 가짜 READ를 추가하지 않습니다.

30개 전부 각 반복의 i 값과 대조했습니다. i=0~3이면 32(공백), i=4이면 10(줄바꿈)이며, `conditionTruth`, `selected`, `skipped`, 실제 printf 인자가 일치합니다. 선택되지 않은 값을 계산하거나 추가 출력을 만들지 않습니다.

생성 근거는 `scripts/model/ir-plan.mjs` 352~355행의 조건 선택 바인딩입니다. `docs/design/c-model.md` 392행과 `docs/design/model-audit-2026-11-04.md`의 FLOW 규칙에도 명시되어 있습니다.

### `-5`: 컴파일러가 접은 소스 연산의 CALC 1개

```c
yrvZEcPOhc[3] = -5;
```

```text
과거: x240 WRITE B[3] = -5

현재: x250 CALC 단항 - : 입력 5 → 결과 -5
      x251 WRITE B[3] = -5, dataInputs=[x250]
```

C AST에서 `-5`는 정수 리터럴 5에 단항 `-`를 적용한 식입니다. LLVM에서는 상수 -5로 접혔지만, 현재 계약은 소스의 계산을 시각화할 CALC로 남깁니다.

이것을 별도의 CPU 실행으로 기록하지 않습니다. `evidence`는 `compiler-folded source calculation at observed consumer`이고, 결과는 실제 저장에서 관찰한 -5입니다. CALC 입력은 5 하나이며, 다음 WRITE의 값과 생산자 연결을 확인했습니다. 메모리 쓰기는 여전히 한 번입니다.

생성 근거는 `scripts/model/ir-plan.mjs`의 `hasCalculation`·`folded`, `scripts/model/ir-record.mjs`의 `emitFolded`입니다. `docs/design/c-model.md` 207행에 컴파일러가 접은 계산을 실제 상수 소비값과 연결하는 계약이 있습니다.

## 사건 수와 별개로 발견한 순서 차이

17행 `C[i] = A[i] + B[i]`의 5회 반복에서 각각 두 사건의 순서가 다릅니다.

```text
과거: A[i]·B[i] 읽기 → 대상 인덱스 i 읽기 → 덧셈 CALC → C[i] 쓰기
현재: A[i]·B[i] 읽기 → 덧셈 CALC → 대상 인덱스 i 읽기 → C[i] 쓰기
```

첫 반복의 과거 공개 기록은 `x172 READ i → x173 CALC +`입니다. 그러나 그때의 원시 기록도 이미 `e334 add → e335/e336 load i`였습니다. 과거 변환기가 CALC를 뒤늦게 내보내던 순서였습니다.

현재 공개 기록은 `x182 CALC + → x183 READ i`이며 현재 원시 기록 `e320 add → e321/e322 load i`와 일치합니다. 5회 모두 같은 관계를 확인했습니다. 연산의 데이터 입력은 여전히 A[i]·B[i]의 READ 두 개이고, 대상 인덱스 READ는 WRITE의 주소 입력입니다. 값이나 쓰기 대상은 달라지지 않았습니다.

추가 31개를 제외한 610개는 이 5쌍의 순서 차이를 대응시킨 뒤 위 비교 필드가 모두 일치했습니다. 객체의 ID·주소·크기·생성 및 소멸 시점도 대응되며, 출력 6줄도 동일합니다. 전체 JSON이 같다는 뜻은 아닙니다. 조건 선택의 제어 연결, 자료형, 출력 출처 등의 메타데이터는 후속 보완으로 달라졌습니다.

## 왜 기존 검사가 뒤처졌는가

Git 기록에서 다음을 확인했습니다.

- `3495d10` — 2026-11-03: `tests/ir-array-metadata.test.js:30`에 610개·CALC 124개 고정 단언이 들어갔습니다. 이 단언은 현재까지 그대로입니다.
- `4449b46` — 2026-11-04: 삼항 선택을 `FLOW/conditional`로 내보내는 경로와 접힌 단항 계산을 CALC로 남기는 경로가 들어갔습니다. 해당 커밋의 실제 코드에도 두 경로가 있습니다.

따라서 이번 실패의 원인은 오래된 총개수 기준입니다. 다만 610을 641로 바꾸는 것만으로 과정 검증이 충분해지는 것은 아닙니다. 삼항식 30회의 선택과 전달, 상수 계산의 단일 WRITE 연결, 실제 순서·수명 등을 검사하는 것이 변경 의미에 더 직접적입니다. 이번 요청에서는 기존 검사 기준을 그대로 보존했습니다.
