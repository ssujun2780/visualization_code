# 그래프 표현별 추론 비교

## 범위와 고정 기준

자료구조 추론 검사만 수행했습니다. 생성 모델·추론기·UI는 수정하지 않았습니다. 기존 전체 예제를 재실행하지 않았습니다.

적용한 계약은 `inference-model.md`의 읽기 전용 소비자 경계, `structure-presentation-policy.md`의 추천 범위·사용자 지정·실행 사실 보존, `structure-common-fixes-2026-11-09.md`의 실제 인덱스 전달·속성·변경 근거입니다.

입력을 먼저 작성하고 `expectations.json`에 소스 SHA-256, 출력, 정점 식별자, 간선 양 끝·중복 수·가중치, 변경 후 관계를 고정했습니다. 실제 결과에 맞춰 기대값을 변경하지 않았습니다. 대조 예제는 별도 `control-expectations.json`으로 추가했습니다.

기본 그래프는 정점 0~5와 다음 다섯 간선입니다. 4와 5는 처음에 고립되어 있습니다.

```text
0 → 1 :  0
0 → 2 :  4
1 → 3 : -2
2 → 3 :  7
3 → 3 :  5
```

변경 단계에서는 `0→2`를 제거하고 `4→2 : 9`를 추가합니다. 삭제된 간선의 저장 공간이 남아 있어도 현재 인접 관계에는 포함되지 않아야 합니다. 평행 간선 검사는 `1→3 : 6`을 별도로 추가했습니다.

## 보완점 1: 구조 관계 발견이 비교 실행에 의존

각 구현은 실제 간선의 목적지·가중치를 읽은 뒤 다음 조건을 실행합니다.

```c
int v = p->to, w = p->weight;
if (d[u] != 10000 && d[v] > d[u] + w) {
    d[v] = d[u] + w;
    seen[v] = 1;
}
```

새 간선은 정점 4에서 출발합니다. `d[4]`가 10000이므로 두 번째 비교가 생략됩니다. 02의 중간언어는 다음을 정확히 기록했습니다.

```text
x916 READ  d[4] = 10000
x917 CALC operators: !=, &&
     evaluation.right = skipped
     evaluation.reason = and-left-false
x918 FLOW branch: false
```

그런데 그래프는 기존 비교의 양쪽 정점 접근을 주요 근거로 생성하므로 새 간선을 놓칩니다. `index-domain-views.mjs`는 비교 피연산자의 인덱스 관계를, 행렬 경로인 `traversal-graph-views.mjs`도 실제 비교 단계의 두 축을 사용합니다.

09는 저장 구조·간선 변경·예상 출력을 그대로 두고 `if(d[v] > d[u]+w)`로 바꾼 **별도 대조 입력**입니다. 이 경우 `4→2 : 9`가 나타났습니다. 원래 02나 기대값을 수정한 것은 아닙니다.

제안: 확인된 정점 영역·인접 저장소·목적지 필드·속성 역할을 재사용하여, 실제 순회에서 읽힌 새 간선을 복원합니다. 비교는 역할 발견 근거 중 하나로 사용하고, 이미 확인한 구조의 매 간선이 비교까지 실행되어야 한다는 의존을 제거합니다. 미확인 필드를 이름이나 정수값만으로 목적지로 취급해서는 안 됩니다. 중간언어의 단락 평가는 그대로 유지합니다.

## 보완점 2: 정점 구성원을 간선 끝점에서만 생성

예상 정점은 `0,1,2,3,4,5`지만 초기 실제 후보의 구성원은 `0,1,2,3`입니다. 두 그래프 모듈 모두 발견된 간선의 양 끝점에서 논리 노드를 추가합니다. 기존 `coverage`에도 고립 정점이 미확인이라고 적혀 있으므로, 완전한 결과라고 거짓으로 확정한 것은 아닙니다.

제안: 간선 집합과 정점 영역을 분리합니다. 이미 확인한 그래프의 헤드 영역·행 영역, 실제 순회 범위·빈 행/NULL 헤드 등으로 정점 구성원을 확인하고 고립 정점도 포함합니다. 배열 용량만으로 사용하지 않은 예약 슬롯을 정점으로 만드는 규칙은 피해야 합니다. 정점 수가 미확정이면 그 상태와 근거를 유지합니다.

## 보완점 3: 삭제 이후 부재 확인이 끝나지 않음

변경 후 `0→2`는 `observed`에서 `unconfirmed-after-write`로 바뀝니다. 따라서 삭제된 간선을 현재의 확정 간선으로 계속 표시하는 오류는 막고 있습니다. 그러나 해당 행/목록을 다시 끝까지 순회한 뒤에도 삭제를 확인한 상태로 전환하지 못합니다. 비교를 항상 실행하는 09에서도 같습니다.

제안: 먼저 관련 쓰기로 기존 관계를 무효화하는 현재 규칙은 유지합니다. 이후 종료가 확인된 같은 행/인접 목록의 재관측이나 확인된 부재 조건으로 현재 구성원을 갱신합니다. 이력과 살아 있는 분리 저장소는 보존하되, 현재 간선에서 빠진 이유를 구분합니다. 중단된 순회나 단순히 읽히지 않았다는 사실만으로 간선을 삭제해서는 안 됩니다.

## 보완점 4: 전체 그래프와 부분 저장 구조의 추천 범위 혼동

02에서 `head` 배열 전체를 선택하면 초기 추천은 `graph`가 1위입니다. 변경 후에는 다음처럼 바뀝니다.

```text
stack → binary-tree → linked-list → tree → array
```

1위는 `head[0]`에 대응하는 한 원소짜리 연결 리스트 후보입니다. 이 후보의 `representedNodeCount=1`, `familyNodeCount=1`은 그 후보 내부의 범위이지, 선택한 전체 인접 목록의 범위가 아닙니다. 09에서 논리 간선이 모두 복원되어도 같은 추천 문제가 남습니다.

CSR의 `seen`에는 실제로 쓰기가 발생한 부분 연결 `0→1, 0→2, 1→3`이 생기고 `binary-tree`가 1위입니다. 이 부분 연결의 모양 자체는 트리일 수 있으므로 곧바로 틀린 위상 판정이라고 단정하지 않습니다. 다만 정점 상태 배열·작업에서 선택된 연결·원래 전체 그래프를 구별할 역할과 범위가 부족합니다.

제안: 전체 선택 영역과 개별 헤드·작업 배열의 범위를 분리해 추천합니다. ‘인접 목록의 저장 방식’과 ‘그 목록이 나타내는 그래프’를 다른 관계 계층으로 유지하고, 부분 후보의 내부 완전성을 전체 선택 범위의 완전성으로 점수화하지 않습니다. 한 셀을 선택했을 때의 리스트/스택 후보는 유지합니다. 추천 상위 5개와 사용자 지정 우선 규칙도 그대로 유지합니다.

## 오류로 세지 않은 항목

- 0과 음수 가중치는 간선의 해당 저장 위치에 올바르게 연결됐습니다. 정점 거리 `d`나 상태 `seen`이 가중치로 섞인 사례는 없었습니다.
- 속성의 `role`은 `meaning unconfirmed`입니다. 값의 연결과 ‘가중치’라는 의미의 자동 확정은 별개이며 후자는 기존 한계입니다.
- 대칭 행렬의 양방향 저장을 자동으로 무방향 간선 하나로 합치지 않았습니다. 대칭이라는 이유만으로 사용자 의도를 확정하지 않은 정상적인 보수적 처리입니다.
- CSR의 가중치 없는 순회 관계는 가중치 후보의 대안이며, 그 자체를 속성 유실 버그로 단정하지 않았습니다.
