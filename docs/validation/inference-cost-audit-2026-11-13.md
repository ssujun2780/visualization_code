# 공통 추론기 비용 분석

2026-11-13. **분석과 개선 제안만 수행했습니다. 생성 모델·공통 추론기·테스트 동작은 변경하지 않았습니다.** 측정용 사본과 분석 스크립트는 `test-results/inference-cost-audit-2026-11-13/`에 있습니다.

## 측정 방법과 경계

기존 8/16/32노드 C 실행 기록을 읽어 추론만 실행했습니다. 컴파일·C 실행은 다시 수행하지 않았습니다. 각 크기는 독립된 Node 프로세스에서 실행했고, 파이프라인 사본에 단계 타이머를 삽입하여 Node CPU 프로파일을 수집했습니다. JSON 직렬화와 산출물 분석은 추론 시간 밖에서 측정했습니다.

세 결과 모두 원본 입력이 불변이며, 측정 사본의 전체 출력 SHA256이 이전 실제 추론 결과와 일치했습니다. 생산 경로의 변경이나 검증 생략은 없습니다. 프로파일러 오버헤드와 환경 변동을 포함한 단일 실행 수치이므로 성능 보장값은 아닙니다.

이전 `190MB`는 RAM이 아니라 **직렬화된 추론 JSON의 189,662,263바이트**였습니다. 당시 테스트 프로세스 RSS는 약 919MB였습니다. 독립된 이번 32노드 실행은 추론 직후 RSS 약 485MB, JS heapUsed 약 284MB였습니다. 이후 JSON 분석까지 포함한 프로세스 최고 RSS는 약 851MB이므로 이를 추론만의 최고 사용량으로 해석하면 안 됩니다.

## 공통 원인

### 1. 모든 변화에 모든 루트 상태를 다시 만듭니다

`linked-views.mjs:423~479`는 객체 생성·종료, 포인터 읽기/쓰기 등으로 `changed`가 되면 모든 루트에 `state(c,e)`를 호출합니다. `state`는 후보마다 전체 같은 타입의 레코드, 연결, 이웃 관계, 도달 집합, 역할별 위상을 다시 계산합니다(`342~416`).

이번 210개 후보에는 `main.pool`의 32개 포인터, 재귀 `join` 매개변수 `b`의 129개 호출 객체, 반복문의 `p` 32개 등이 포함됩니다. 이들은 서로 겹치는 실제 관찰 위치이므로 전부 잘못된 후보라고 삭제할 수 없습니다. 문제는 각 위치의 관찰 권한과 전체 구조·이력을 별도 복제하는 비용이 결합되어 있다는 점입니다.

또한 루트 수명 기준으로 분류하면 생성 전 상태 3,434개/12.14MB, 종료 후 상태 8,900개/49.64MB입니다. 루트가 살아 있는 동안은 10,001개/104.62MB입니다. 사라진 지역 포인터의 공간과, 여전히 살아 있는 힙 객체의 관계를 분리해서 관리해야 합니다.

### 2. 후보 밖 저장소 정보가 모든 후보에 반복됩니다

연결 후보 170.31MB가 전체 결과의 **89.8%**입니다. 그 상태 필드 중:

- `unrelatedStorage`: 35.61MB.
- `associatedStorage`: 19.21MB.
- `edges`: 33.49MB.
- `topology`, `storageTopology`, `roleTopologies`: 합계 약 56.88MB(래퍼 포함).

관련 없는 새 레코드가 생겨도 `unrelatedStorage`가 달라져 많은 후보에 새 전체 상태가 저장됩니다. 외부 저장소 세 필드와 시점/최상위 근거 ID를 분리하여 비교하면 22,335개 중 **17,796개(79.7%)**가 직전 상태와 같은 핵심 내용입니다. 외부 정보를 버리라는 의미가 아니라, 공통 저장소 이력에서 별도로 조회할 수 있는 중복입니다.

위상 객체 내용만 정확한 동등성으로 집계하면 67,005회/54.36MB가 저장됐지만 고유 내용은 1,253개/5.88MB입니다. 참조·색인 비용을 제외한 잠재적 공유량이며, 최적화를 구현하여 얻은 결과 크기는 아닙니다.

### 3. 중복 검사를 위해 큰 상태 두 개를 매번 문자열로 만듭니다

`linked-views.mjs:417`:

```js
if (!prev || JSON.stringify({...prev, afterExecutionId:null}) !==
             JSON.stringify({...row, afterExecutionId:null})) c.states.push(row);
```

후보 상태를 이미 전부 계산한 다음 이전/현재 상태를 직렬화해 비교합니다. CPU 위치 표본도 이 줄에 집중됐습니다. 최종 결과를 파일로 직렬화하는 비용과 별개의 내부 반복 직렬화입니다. 단순히 JSON 저장을 끄거나 출력 압축을 해도 이 계산 비용은 남습니다.

### 4. 수명·도달 관계 조회가 반복 선형 검색입니다

- `pointer-tree-views.mjs:104`의 `live()`는 매번 `objects.find(...)`를 수행합니다. CPU 자체 시간 표본은 약 1.51초입니다.
- `pointer-semantics.mjs:50~63`의 공유 관계는 사건마다 루트 쌍을 순회하면서 같은 루트의 도달 집합을 다시 구합니다. 인접 간선도 반복 `filter`합니다.
- 포인터 우선순위 후보도 비교 정책·근거 목록·간선을 상태마다 반복 포함합니다. 하나의 후보에서 539개 상태/13.01MB가 나왔습니다.

1과 4는 현행 표현을 대체로 유지하면서 시작할 수 있습니다. 저장량을 크게 줄이려면 2와 3의 공통 이력 구조 보완까지 필요합니다. 단순 후보 수 제한, 프레임 무시, 기록 잘라내기, 검증 생략, 생성 모델 변경으로 해결하지 않습니다.

공통 관계의 최신 버전 하나만 저장하는 방식도 충분하지 않습니다. 원하는 과거 시점의 상태를 재생해야 하므로 버전별 변경분/체크포인트와 관측 시점이 필요합니다. 같은 대상에 접근하는 두 포인터를 하나의 사용자 변수로 합치는 것은 별개의 잘못된 변경입니다.
