## 실행 전에 정한 기대와 실제 결과

새 C 소스와 `.expected.json`은 `traceModel` 호출 전에 기록합니다. 원소는 pear/1, apple/5, apple/9, melon/2이며 문자열 오름차순·동점 숫자 내림차순 정책이면 루트는 apple/9입니다. 정렬 정책 `[1,-1]`, 힙 상태 정상 → 루트 문자열을 zzz로 바꾼 뒤 위반을 기대했고 일치했습니다. 역방향은 `[-1,-1]`와 pear 루트를, 문자열 단독은 `[1]`을 별도로 검사했습니다.

- 문자열을 비교한 뒤 다른 포인터로 교체하고 해제하는 정상 C 코드: 교체 직후 정상, 해제·NULL 뒤 unknown.
- 내장 문자 배열을 종료 바이트 없이 채우되 이후 C에서 읽지 않는 정상 코드: 추론도 종료 바이트를 만들어내지 않고 unknown.
- `strcmp(...) + 1`: 반환 크기에 의존하므로 사전식 정책으로 확정하지 않음.
- 이름만 `strcmp`인 사용자 함수: 표준 문자열 비교로 해석하지 않음.
- 실제 문자열 비교의 바이트 범위를 바꾸거나 재할당 종료를 일반 free로 바꾼 기록: 계약 검증에서 거부.
- 재실행 시 사용자 지정과 조건은 재연결하되, 과거 실행의 바이트·정상 판정을 복사하지 않음.

## 조합 검증에서 발견해 고친 부분

1. 구조체 값 복사: 문자열 정책은 찾았지만 전체 원소 COPY에 첨자 노드가 직접 없어서 인덱스 트리를 놓쳤습니다. 실제 목적지·인덱스와 배열 선언의 신원을 연결했습니다. 변수명/숫자를 맞춘 분기는 없습니다.
2. realloc: 새 배열에 현재 범위는 있으나 재할당 뒤 부모 인덱스 계산을 다시 실행하지 않아 힙 구성원을 놓쳤습니다. 같은 산식/원소 배치와 명시적인 재할당 이력, 유지 바이트를 확인해 관계 근거만 이었습니다. 원래 사건은 새 사건으로 바꾸지 않습니다.
3. 기록 한도: 복합키 상태가 참조한 인덱스 상태를 별도로 버려 검증 실패 후 후보가 제거됐습니다. 보관된 상태의 정확한 의존 시점을 제한된 판정 근거로 보존했습니다. 한도 검사 기대를 낮추지 않았고, 진단은 한도 알림만 남으며 생략된 시점의 조건은 incomplete입니다.
4. 검사 대상 선택: 보조 함수 예제에는 문자열만 비교하는 `lex`와 숫자 동점까지 비교하는 `compare` 후보가 모두 생깁니다. 최초 검사는 첫 후보를 골라 기대와 달랐습니다. C 소스에서 검사하려던 `compare` 선언을 명시하도록 선택부만 고쳤습니다. 기대 키 순서·구성원·정상/위반 판정은 유지했습니다. 함수 이름을 사용하는 이 선택은 테스트에만 있으며 추론기에는 없습니다.

## 한계
