이번 작업은 조사입니다. 중간언어 생성 모델·추론기·UI·기존 테스트는 수정하지 않았습니다.

20개 새 구현과 반례, 2개 동등한 대조 구현을 실행했습니다. 실행 전 소스·표준 출력·시점별 기대 관계를 고정했습니다. 총 22개 코드, 37개 검사 시점입니다. 모든 프로그램이 예상 출력으로 정상 종료했으며, API가 보고한 IR gap·unexplained 항목은 없었습니다. 이것이 모든 중간언어 사건의 정확성을 증명하는 것은 아닙니다.

## 검사 기준

- 같은 값을 가진 노드도 객체 식별자·오프셋·필드 위치로 구별합니다.
- 저장된 간선, 현재 루트의 구성원, 논리적 부모/자식, BST·힙 의미를 별도로 비교합니다.
- 미사용 배열 칸과 이전 링크를 현재 구성원으로 자동 편입하지 않습니다.
- 공유 자식·순환·잘못된 부모 링크는 구조상의 반례입니다. 예제 자체는 범위 밖 접근이나 미초기화 값 읽기 없이 정상 실행합니다.
- 추론기의 내부 후보 종류가 다르다는 이유만으로 실패 처리하지 않습니다. 18번은 `linked-structure`가 아닌 저장 관계 그래프를 통해 정확한 4노드 트리를 추천합니다.

## 새 보완점 8개

### 1. 삼항식으로 작성한 종료 조건을 놓침

07번의 종료 조건은 다음과 같습니다.

```c
return p < 0 ? 0 : 1 + walk(a, a[p].lo) + walk(a, a[p].hi);
```

실제 기록에는 `FLOW/conditional`과 조건값이 있습니다. 예를 들어 x175의 조건은 참이고, 선택한 가지에서 0을 반환합니다. 그러나 `terminationEvidence`는 0건이며 음수 링크가 종료 경계로 확정되지 않습니다. 같은 문제는 분리 배열 08번과 표 형태 10번에서도 나타납니다.

21번 대조군은 같은 종료 조건만 `if (p < 0) return 0;`으로 풀었습니다. 출력과 기대 구성원은 그대로이며, 종료 근거가 S0에서 6건, S1에서 12건 생깁니다.

원인: `traversal-boundaries.mjs`가 `action === 'branch'`를 찾고, 명시적 분기 종료와 순회 전달을 연결합니다. `conditional`의 선택 가지와 반환 연결은 소비하지 못합니다.

공통 보완 방향: AST 조건·선택된 가지·실제 값 전달·순회 억제를 공통 조건 근거로 연결합니다. 삼항식이라는 이름만 보고 종료로 간주하거나, 음수라는 이유만으로 센티널 처리하지 않습니다. 기존 중간언어 사건을 추론기가 읽는 개선입니다.

### 2. 인덱스 루트에서 여러 자식 역할을 합치지 못함

07·08·10·21번은 왼쪽/오른쪽 자식을 모두 따라야 한 트리입니다. 21번의 루트 6에는 구성원 `{6,1,0,3,5}`가 있습니다. 실제 루트 후보는 lo 경로 `[6,1,0]`, hi 경로 `[6,5]`로 나뉩니다. 추천 첫 항목도 5노드 트리가 아니라 2노드 linked-list입니다.

원인: `indexed-root-views.mjs`는 루트별로 다시 **개별 role**을 순회하고, 한 노드당 간선 하나인 경로를 구성합니다. 전역 저장 간선은 맞지만, 루트에서 여러 자식 역할을 함께 따라가는 보기가 없습니다. 종료 조건을 고치는 것만으로 해결되지 않는 별개 문제입니다.

공통 보완 방향: 실제 순회 근거로 함께 쓰인 자식 역할 집합을 만들고 그 집합의 도달성을 계산합니다. 단일 역할 보기와 전체 보기를 함께 보존하며, 부모·캐시 역할까지 무조건 합치지 않습니다.

### 3. 포인터 자식 배열의 사용 개수를 적용하지 못함

04번은 `N *child[4]`와 `used`를 두고 `i < p->used`인 칸만 순회합니다. 이전 링크를 미사용 칸에 남겨둡니다.

루트의 used를 3→2로 줄이면 현재 트리는 5→4개가 되어야 합니다. 출력은 그렇게 바뀌지만 실제 추천은 계속 `graph / partial / 5 nodes`입니다. 자식 배열 전체를 하나의 트리 관계로 묶는 것도 불충분합니다.

원인: 현재 record prefix 연결은 주로 정수 인덱스 배열 관계에 적용됩니다. 포인터 배열의 관측 슬롯과 개수 조건에는 같은 구성원 규칙이 연결되지 않습니다.

공통 보완 방향: 표현이 포인터인지 정수인지와 별개로, 조건의 관리 변수→순회 인덱스→슬롯 범위 관계를 적용합니다. 개수가 바뀌면 현재 구성원도 갱신하되, 비활성 슬롯의 실제 포인터는 삭제하지 않습니다. used가 0인 노드도 관측한 조건으로 설명해야 합니다.

### 4. 부모 포인터만 저장한 전체 트리를 놓침

06번은 각 노드에 `up`만 있습니다. 루트 3과 연결된 6개 노드를 부모 방향으로 읽습니다. 실제 up 간선은 맞지만 추천에는 2노드 등의 개별 상향 체인만 나타납니다. 같은 계열의 부모 인덱스 배열인 09번에서는 전체 forest/tree가 나옵니다.

공통 보완 방향: 관측된 부모 후보 관계의 연결 성분, 종료 경계, 각 노드의 부모 수와 순환 여부를 검사해 전체 구성원을 묶습니다. 자식 방향 배치는 역방향 보기로 제공하고 실제 포인터 방향은 보존합니다. 단일 후속 링크라는 이유만으로 항상 부모라고 확정하지 않습니다.

### 5. 첫 자식·다음 형제의 논리적 부모 관계가 없음

05번의 물리 연결은 다음과 같습니다.

```text
4.child = 2; 2.sibling = 6; 6.sibling = 1;
2.child = 5; 6.child = 0; 0.sibling = 3;
```

실제 물리 그래프는 7노드 이진 형태로 정확합니다. 그러나 의도한 일반 트리는 `4 → {2,6,1}`, `2 → {5}`, `6 → {0,3}`입니다. 현재는 형제 연결을 같은 부모의 자식으로 펼친 논리적 보기가 없습니다.

공통 보완 방향: 부모에서 자식 순회를 시작하고, 반복문에서 형제 관계를 따라 재귀 호출하는 실제 데이터·제어 흐름을 근거로 역할 후보를 만듭니다. 필드 이름만으로 child/sibling을 판정하지 않고, 물리 연결과 논리적 부모 관계를 모두 보존합니다.

### 6. 추천 후보의 전체 범위와 부분 범위 계산이 부정확함

05번 실제 추천 메타데이터:

```text
linked-list: representedNodeCount=3, familyNodeCount=3, omittedNodeCount=0
binary-tree: representedNodeCount=7, familyNodeCount=3, omittedNodeCount=0
```

부분 경로를 전체 크기의 기준으로 삼아 7개를 담은 후보가 전체 3개보다 커집니다. 3노드 리스트가 첫 추천으로 올라옵니다.

02번 S2에서는 hi 역할만 보는 stack 후보가 첫 추천입니다. 해당 경로의 구성원은 1개이고 전체 트리는 2개인데, `representedNodeCount=null`, `familyNodeCount=2`, `omittedNodeCount=0`입니다. 과거 hi 끝 삽입·삭제는 실제 관측됐으므로 **그 역할의 행동 근거 자체가 조작된 것은 아닙니다**. 범위 표기와 순위가 문제입니다.

원인: `structure-presentation.mjs`가 선택된 부분 topology의 nodeCount를 family 기준으로 사용하며, endpoint 정책 후보에는 구성원 수를 붙이지 않습니다. 누락 수가 없을 때 0으로 계산됩니다.

공통 보완 방향: 사용자가 선택한 루트/저장소 범위, 역할별 구성원, 전체 후보 구성원의 식별자 집합을 각각 비교합니다. 수를 모르면 unknown으로 남기고 전체를 담았다고 간주하지 않습니다. 부분 트리·경로 추천은 유지하되 우클릭 상위 5개에서 전체 대상과 혼동되지 않도록 순위·범위를 정합니다.

### 7. 배열 내부 포인터를 받는 보조 함수 때문에 힙 비교 연결이 끊김

11번은 실제 최소 힙 삽입을 하고, 교환만 `exchange(a+p, a+i)`로 호출합니다. 22번은 그 교환을 같은 위치에 세 대입문으로 풀어 쓴 대조군입니다.

| 결과 | 11 보조 함수 | 22 직접 교환 |
|---|---|---|
| 현재 구성원 | 5개 | 5개 |
| 부모/자식 인덱스 관계 | 일치 | 일치 |
| S0 최소 순서 검사 | satisfied | satisfied |
| 비교 방향 | null | min |
| S0 min-heap 추천 | 없음 | 있음 |
| 루트값을 50으로 바꾼 S1 | 순서 위반 기록 | 순서 위반 기록, 힙 추천 해제 |

원인: 보조 함수의 내부 포인터로 겹치는 배열 보기가 생기면서 비교 피연산자가 다른 arrayId에 연결됩니다. `index-relations.mjs`는 동일 arrayId를 요구하므로, 같은 원본 배열의 실제 슬롯 비교를 부모·자식 비교로 연결하지 못합니다.

공통 보완 방향: 현재 객체·오프셋·접근 폭·원소 크기·배열 도메인 관계로 별칭 보기를 연결합니다. 같은 값이라는 이유로 연결하면 안 되며, 과거 값의 복사 출처와 현재 슬롯 관계도 구별해야 합니다.

### 8. 읽기 중심의 암시적 트리에서 활성 범위를 놓침

12번은 `a[12]` 중 `used=5`를 사용하고, `2*i+1`, `2*i+2`가 used 미만일 때만 자식을 읽습니다. 삽입·삭제나 키 비교는 없습니다.

인덱스 트리 후보는 나오지만 `activeRange.count=null`입니다. 5개에 대한 완결된 구성원 보기와 4개 활성 간선을 만들지 못합니다. 저장 용량을 대상으로 한 순서 검사에는 사용하지 않는 뒤쪽 0까지 들어가 최소 순서 위반 샘플 `[5,6,7,8,9,10]`이 남습니다.

이는 실제 프로그램 오류 경고가 아니며, 원본 상태에는 `scope: physical-capacity-candidate`가 있습니다. 이 정보를 현재 논리 트리의 위반으로 사용해서는 안 됩니다.

원인: `index-relations.mjs`의 활성 범위는 array-structure의 length 역할에 의존합니다. 이번 읽기·경계 검사 형태에서 해당 역할이 확정되지 않아 용량 기반 후보로 남습니다.

공통 보완 방향: 실행된 순회 범위·관리 변수·인덱스 주소 관계를 연결해 읽기 중심 구현도 범위 후보를 갖게 합니다. 단순히 접근한 최대 인덱스+1을 길이로 정하지 않습니다. 확정 전에는 물리 용량의 조건 검사와 논리 구성원 검사를 구별하며, 힙이라는 의미는 별도 비교 근거가 없으므로 추천하지 않는 현재 보수적 동작을 유지합니다.

## 기존 미구현 범위: BST

17번은 실제 키 비교 검색을 수행하는 4노드 BST입니다. 이후 왼쪽 서브트리의 7을 12로 바꿉니다. 바로 위 부모 5와의 순서는 맞지만 루트 10의 왼쪽 서브트리 조건은 위반합니다.

실제 결과는 두 시점 모두 binary-tree 4개입니다. BST 추천·조상 범위 위반 판별은 없습니다. 이는 [표현 정책](../design/structure-presentation-policy.md)에 명시된 기존 미구현 기능이며, 이번에 새로 망가진 기본 연결 추론으로 세지 않습니다.

향후에는 실제 키 비교와 검색 방향에서 키 역할·비교 규칙을 찾고, 전체 조상 경계 및 중복값 정책을 검증해야 합니다. 일반 트리로 사용자 지정한 경우 BST 조건을 강제로 적용하면 안 됩니다.
