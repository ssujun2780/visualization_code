## 검사 후 보완한 공통 원인

1. 표시 상태를 단계 사이에서 먼저 줄이면 후속 판정의 입력도 지워졌습니다. 출력 보관과 분석 입력을 분리했습니다. 스트리밍 생성기는 기본 한도를 유지하면서 최신 상태까지 처리하고, 요청한 더 작은 출력 상한은 판정 뒤 적용합니다.
2. 지연 갱신 검증이 생략된 구간 상태를 직접 참조했습니다. 실제 원본 사건으로 확인 가능한 자식 출처는 사건에서 검사하고, 필요한 구간 체크포인트는 별도 한도 있는 `proofStates`로 보존합니다. 과거 근거를 현재 상태처럼 조회하지 않는 검사와 근거 변조 거부 검사도 통과했습니다.
3. 큐 검증기가 작업 번호와 상태 배열 번호를 같다고 가정했습니다. 실제 완료 사건으로 연결하고, 모든 enqueue/dequeue의 FIFO 원소 식별자 검사는 그대로 수행합니다. 상태가 없는 경우 명시된 생략 구간 안인지 검사합니다.
4. 늦게 처리한 구조 종료가 이미 끝난 메모리의 대응 종료 시점을 뒤로 미뤘습니다. 실제 객체 종료와 구조 이탈 중 더 이른 시점에서 닫습니다. 큐의 논리 순서도 실제 원소 범위로 교환합니다.
5. 재귀적인 의존성 탐색이 명시된 탐색 예산보다 먼저 JavaScript 호출 스택에 걸릴 수 있었습니다. 순서를 유지한 반복 탐색으로 바꾸고 1만 사건에서 한도 부족/충분을 각각 확인했습니다.
6. 후보 없이 끝나는 루트·격자·라벨·비교 근거 한도와 상태 내부의 원소/간선 생략도 공통 진단으로 구분했습니다. 생략된 구성원은 정상 조건·추천의 근거로 재사용하지 않습니다.

검사 자체의 초기 설정 오류도 구별했습니다. 한도 5보다 실제 상태가 적은 사례에 무조건 `partial`을 요구하던 조건을 실제 **한도 초과 여부**로 정정했습니다. 실행 관계의 계약상 지원되는 정적 노드 대응은 저장 범위·발견 시점·수명을 별도로 검사하도록 했습니다. 동적 대응 존재·누락 검사, 고정된 합계·원소 순서·식별자 기대값은 유지했습니다. 직접 생성기 검사에는 요구되는 값 흐름 문맥을 전달하고, 자식 포인터를 실제로 순회하는 트라이 사례를 사용했습니다. 실패를 통과로 바꾸기 위해 생성 결과의 값을 정답으로 저장하지 않았습니다.

## 완료 범위와 지원 경계

앞서 남긴 두 작업인 공통 이력·수명·근거 한도 계약과 관련 통합/규모 검증 경로를 구현하고, 위 검사에서 발견된 문제를 보완했습니다. 전체 프로그램 공간의 추론 완전성이나 모든 규모의 성능 상한을 보증하는 의미는 아닙니다.
