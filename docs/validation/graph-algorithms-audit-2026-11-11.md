## 1. 같은 CALC의 복수 관계 근거를 구별하지 못하는 검증 오류

```c
int a = root(edges[best].from), b = root(edges[best].to);
if (a != b) {
    if (sizes[a] < sizes[b]) { int tmp = a; a = b; b = tmp; }
    parent[b] = a;
}
```

실제 `x237 CALC sizes[a]<sizes[b]`에 서로 다른 관계 근거가 두 개 있습니다.

| 근거 | 목적지 출처 READ | 명령 위치 | 관계 |
| --- | --- | --- | --- |
| 첫째 | `x193 edges[best].from` | `i87` | `2→0` |
| 둘째 | `x212 edges[best].to` | `i95` | `0→2` |

이후 `x393` 읽기의 역할은 둘째 근거 `i95`를 재사용합니다. 그러나 `graph-storage-contract.mjs`가 `s.evidence.find(p => p.executionId === learnedFrom)`으로 첫째만 가져와 다음 오류를 냅니다.

```text
stage: indexDomainStructures
자료구조 후보: 재사용 역할과 최초 읽기의 연결이 다릅니다.
```

직전 보완에 추가한 검증 경로의 오류입니다. 실행이나 중간언어의 실패가 아닙니다. `06_kruskal_dsu-rejected-candidates.json`과 `comparison.json`에 제외된 후보와 충돌 근거를 보관했습니다.

**수정 방향:** 사건 ID와 관계 근거 ID를 분리하고, 원래 끝점·소스 접근·속성 역할을 포함하는 고유 근거를 역할 발견 시점에 연결해야 합니다. 검증기는 그 근거를 정확히 조회해야 합니다. 검증을 끄거나 아무 근거 하나가 맞으면 통과시키는 방식은 피해야 합니다. 이 오류를 고친다고 입력 그래프·MST까지 모두 복원된다고 단정할 수는 없습니다. 제외된 영역은 `sizes` 기반 관계입니다.

## 2. 무가중치 행렬의 관계 발견 경로 부족

```c
if (matrix[u][v] && !flags[v]) {
    flags[v] = 1;
    queue[t++] = v;
}
```

`x56 READ matrix[0][1]=1`, `x77 READ matrix[0][2]=1`이 존재합니다. 하지만 `traversal-graph-views.mjs`의 행렬 경로는 같은 정점 배열의 양쪽 접근을 비교하는 계산을 주요 근거로 삼습니다. 이 BFS에는 그런 비교가 없어 최초 역할을 만들지 못합니다. 앞서 보완한 ‘이미 발견한 역할의 재사용’에도 진입하지 않습니다.

**수정 방향:** 행렬 두 축의 실행 커서, 셀에 대한 조건 분기, 목적지 상태 접근 또는 작업 목록 전달을 조합하는 관계 어댑터가 필요합니다. 일반 표의 조건 검사만으로 그래프를 만들지 않도록 축과 목적지 전달을 검증해야 합니다. 중도 종료 후 아직 읽지 않은 행과 큐에 남은 정점을 완료·부재로 판정해서는 안 됩니다.

## 3. 개수 기반 인접 행을 ‘다음 행 접근’으로만 확인

```c
for (int k = 0; k < lengths[u]; k++) {
    int v = rows[u][k];
    degree[v]--;
    if (degree[v] == 0) queue[t++] = v;
}
```

실제 읽기는 다음 여섯 개 모두 있습니다.

```text
x122 rows[0][0]=2   x170 rows[1][0]=2
x198 rows[1][1]=3   x251 rows[2][0]=4
x299 rows[3][0]=4   x352 rows[4][0]=5
```

실제 후보에는 `1→2`, `1→3`, `3→4`만 남습니다. `0→2`와 `2→4`는 그 시점에 차수가 0이 아니어서 큐에 넣지 않았고, `4→5`의 목적지는 빈 행이므로 후속 행 원소 읽기가 없습니다.

`table-row-views.mjs`는 셀의 값이 나중에 같은 표의 행 인덱스에 도달하는 관계를 확인합니다. 이 규칙 자체는 실제 행 연결을 찾지만, 위상 정렬의 모든 인접 간선을 나타내는 데 충분하지 않습니다. 현재 후보는 `partial`로 표시되어 있으므로 완전하다고 기록한 것은 아닙니다. 다만 일부만 남은 모양의 binary-tree 추천이 전체 표에서 앞서는 문제가 있습니다.

**수정 방향:** 행 식별자·현재 행의 유효 원소 수·실제 목적지 상태 접근을 연결해야 합니다. 큐에 넣혔는지와 간선 존재를 분리하고, 예약된 열을 채우기 원소로 오인하지 않아야 합니다. 부분 관계의 트리 모양은 완전한 관계의 분류보다 강하게 추천하지 않아야 합니다.

## 4. 보조 상태 관계와 원래 그래프의 추천 범위 분리 부족

CSR BFS의 원래 관계는 다음 5개입니다.

```text
0→1, 0→2, 1→3, 2→3, 3→0
```

`marked`에서는 모두 찾습니다. `closed[u]=1`까지 큐를 통해 전달된 인덱스의 출처를 따라가면 다음 3개 작업 관계도 존재합니다.

```text
0→1, 0→2, 1→3
```

이 관계는 출처 추적으로서 유효합니다. 하지만 원래 전체 그래프와 다른 층입니다. 실제 `offsets`, `links`, `closed` 추천은 `forest → array → graph`입니다. 원래 그래프의 순환을 없앤 것은 아니지만, 다른 관계의 모양을 먼저 보여주게 됩니다.

직전 상태 역할 보완은 `index-domain-graph-candidate`와 같은 인덱스 READ를 공유하는 조건부 WRITE에 연결되어 있습니다. 여기서는 원래 관계도 `bounded-index-walk`이고, 완료 WRITE는 발견 조건문 밖의 나중 while 반복에서 일어납니다. 현재 조건에 해당하지 않습니다.

**수정 방향:** 관계를 만든 모듈의 종류나 WRITE의 바로 바깥 조건문에 종속시키지 않고, 원래 연결·큐 전달·상태 갱신의 출처 경로를 공통으로 연결해야 합니다. 원래 그래프, 발견 관계, 완료 상태를 다른 역할로 보존하고, 전체 저장소 선택 시 보조 관계가 우선하지 않도록 해야 합니다. 값 1을 ‘방문 완료’로 해석하는 규칙은 부적절합니다. A 지점에서 `marked[0]=1`, `closed[0]=0`입니다.

## 5. 별도 개수로 비었는지 판단하는 원형 큐 누락

```c
queue[t] = v; t = (t + 1) % 6; n++;
while (n) {
    int u = queue[h]; h = (h + 1) % 6; n--;
}
```

01의 큐 추천은 array뿐입니다. 02·04의 `h<t` 선형 큐는 queue로 추천됩니다. `queue-views.mjs`는 두 커서 간 실제 비교가 없으면 후보 생성을 건너뜁니다. 별도 개수와 모듈러 갱신을 사용하는 이 표현을 현재 다른 경로도 복원하지 못했습니다.

**수정 방향:** 저장소와 두 커서·개수의 연결을 실제 삽입/제거·변경값·모듈러 범위로 확인하고, FIFO 순서를 독립 검증해야 합니다. `n` 같은 이름, 최종 출력 순서, 단순 인덱스 증가만으로 큐를 확정해서는 안 됩니다.

## 6. 구조체 원소를 통째로 이동하는 힙의 연결 근거 부족

```c
int p = (k - 1) / 2;
if (heap[p].key <= key) break;
heap[k] = heap[p];
k = p;
```

다익스트라의 실제 거리는 `[0,2,1,4,4,1000]`, 오래된 힙 항목 건너뛰기는 2회로 예상과 같습니다. 그러나 `indexRelations.candidates=[]`, `heap` 추천은 array뿐입니다.

공개 계획에는 `(k-1)/2`, `2*k+1`, 비교 필드의 AST가 있습니다. 반면 통째 복사하는 목적지 `heap[k]`는 WRITE/copy 및 실제 저장 범위로 기록되며, 해당 명령에는 `expression`이 없습니다. 정적 식 수집기는 읽기 쪽 `heap[p]`·`heap[c]`를 보지만 `heap[k]` 기준 접근을 연결하지 못해 부모·자식 공식 후보가 탈락합니다. `heap-binding-inspection.json`, `heap-ast-paths.json`에 확인 내용을 보관했습니다.

**수정 방향:** 먼저 COPY의 실제 원소 범위·주소 입력·보조 관찰과 커서 버전을 연결해 정적 공식의 근거를 보충해야 합니다. 이어서 구조체의 키 필드와 원소 전체 이동을 구별하고, 현재 점유 범위에 힙 조건을 적용해야 합니다. 기존 추론 입력으로 부족한 메타데이터가 있는지는 따로 확인해야 하며, 이번에는 생성 모델을 수정하지 않았습니다. 실행/복사 누락이 확인된 것은 아닙니다.

## 7. 크루스칼의 세 관계를 연결하는 기능은 별도 확장 항목

실제 선택한 입력 간선 ID는 `[1,3,2,5]`, 가중치 합은 7입니다. 최종 DSU 부모 배열은 `[1,1,1,1,1]`이며, 루트 1의 자기 참조는 `root-termination`으로 처리됩니다. DSU 부모 간선은 `0→1,2→1,3→1,4→1`입니다.

선택한 신장 트리의 간선은 `0—2,1—3,1—2,3—4`입니다. 서로 다른 연결이라는 점을 유지해야 합니다. 현재 DSU 후보가 이 신장 트리라고 표시되지는 않지만, 입력 간선 저장소·선택 ID 목록·DSU를 자동 연결한 보기는 없습니다.

**확장 방향:** 실제 입력 간선 ID의 출처와 조건부 선택 WRITE를 연결해 부분집합 후보를 만들고, DSU 부모 관계는 별도 유지합니다. 그것이 MST라는 의도와 최적성까지 자동 확정하지 않습니다. 검증기 오류 수정과 이 기능의 구현은 다른 작업입니다.

## 정상 동작과 범위 밖 항목

- 포인터 DFS의 순환·공유 자식·고립 노드는 실제 저장 참조에 보존됩니다. 재귀 호출 트리와 혼동하지 않았습니다.
- 다익스트라의 가중치 없는 순회 그래프는 가중 그래프의 대안입니다. 이를 가중치 유실 오류로 세지 않습니다.
- 히스토그램의 인덱스 분배를 탐색 그래프로 오인하지 않았습니다.
- 탐색 완료 의미의 자동 해석·색칠은 미구현 범위입니다. 값 전달과 상태 기록이 맞는 것과 자동 의미 판별은 별개입니다.
- `queryStructureRelations`의 어댑터는 현재 명세상 linked/rooted-index/pointer-tree 계열만 지원합니다. 별도 graph 후보까지 이 API로 통합하는 것은 후속 확장입니다. 후보가 저장되어 있다는 사실과 이 조회가 빈 목록을 반환하는 것을 혼동하지 않습니다.

`prepare.mjs`는 이미 고정한 예상이 있으면 중단합니다. 기존 예상에 덮어쓰지 않습니다.

```powershell
node test-results/graph-algorithms-audit-2026-11-11/run.mjs
node test-results/graph-algorithms-audit-2026-11-11/analyze.mjs
```

결과 폴더의 사례별 JSON에 원본 `plan`, `trace`, 보조 관찰, `inference`, 확인 지점 결과를 함께 저장했습니다. `comparison.json`은 정점 식별자·간선 끝점·중복·가중치 비교와 실패 근거를, `integrity.json`은 구현·원본 기록 불변을 담습니다. 다른 의미의 후보를 전체 그래프와 비교한 차이는 자동으로 오인식 판정하지 않고 이 문서에서 구분했습니다.
