## 1. 해시의 기본 관계 조합이 아직 없음

```c
int b = k % 5;
p->key = k;
p->value = v;
p->next = buckets[b];
buckets[b] = p;

for (Entry *p = buckets[k % 5]; p; p = p->next)
    if (p->key == k) return p->value;
```

01에서 실제 연결은 정확합니다. forest도 그 연결의 기하학적 모양으로 틀린 것은 아닙니다. 그러나 사용 의도인 해시 테이블을 설명하기에는 부족합니다. 현재 추론기는 연결과 위상 후보를 조합하지만 **입력 키 → 계산한 버킷 → 충돌 후보 → 동등 비교 → 값**의 관계를 별도로 만들지 않습니다. 코드에서도 hash/bucket/probe 전용 어댑터가 없는 것을 확인했습니다.

**공통 보완 방향:** 이름이나 `%` 하나를 기준으로 분류하지 않고 실제 키의 값 전달, 주소 인덱스 계산, 후보 키와의 동등 비교, 반환/갱신 값의 대응을 기록합니다. 이미 있는 연결 목록/배열을 하위 저장 관계로 재사용하고 그 위에 associative lookup 후보를 조합합니다. 입력이 다른데 같은 버킷을 쓰는 관측은 충돌 근거로 남깁니다. 반례 05처럼 키 저장·동등 비교가 없는 집계는 구별해야 합니다. 해시 함수가 사용자 함수이거나 비트 마스크여도 같은 값 전달 규칙을 사용해야 합니다.

## 2. 빈 슬롯·점유·삭제 표지 역할을 구별하지 못함

```c
if (table[i].state == 0) return -1;
if (table[i].state == 1 && table[i].key == key) return i;
// 삭제
table[locate(8)].state = 2;
// 삽입 중 삭제된 슬롯을 기억하고 재사용
if (table[i].state == 2 && hole < 0) hole = i;
```

02의 A 지점은 슬롯 `(1: key=1, state=1)`, `(2: key=8, state=2)`, `(3: key=15, state=1)`입니다. 키 15 검색은 삭제 슬롯 2를 지나 슬롯 3까지 도달합니다. B에서는 슬롯 2가 키 22로 재사용됩니다. 값과 과정은 기록돼 있지만 추천은 계속 배열뿐입니다.

**공통 보완 방향:** 숫자 0/1/2에 뜻을 고정하지 않고 분기 결과를 연결합니다. ‘검색 종료’, ‘키 비교 가능’, ‘검색은 계속되지만 삽입에 재사용’이라는 실제 역할을 별도 상태 후보로 둡니다. 충돌 탐사 순서와 슬롯 생애를 표시하되, 관측되지 않은 전이는 모른다고 남겨야 합니다. 연속 접두 구간이라는 동적 배열 규칙을 적용하면 안 됩니다.

## 3. 정수 버킷 루트와 기록 구성원 발견이 순회 범위에 제한됨

```c
int z = k % 3, i = count;
pool[i].key = k;
pool[i].value = k * 10;
pool[i].link = heads[z];
heads[z] = i;
order[count] = i;
count++;
```

04는 네 기록을 실제로 썼지만 검색 `get(5)`가 기록 1에서 반환하므로 기록 0까지 순회하지 않습니다. `record-index-views.mjs`의 현재 구성원은 `[1,2]`이고 `1→0`은 `unresolved-target`입니다. 루트는 heads[2]와 검색 지역 포인터 인덱스만 발견했습니다. 해당 연결 후보가 불완전하다고 표시한 것은 맞으며, 값이 사라진 중간언어 오류는 아닙니다.

**공통 보완 방향:** 실제 읽기로 연결 필드를 확인한 뒤, 동일한 필드의 이미 기록된 WRITE와 초기화·삽입 증거로 구성원을 보충합니다. heads의 다른 원소도 동일한 저장 역할인지 확인해 정수 루트 컬렉션으로 묶습니다. count와 저장소의 인덱스 전달을 연결하되, 용량 8 전체나 padding 값 123을 노드로 만들지 않습니다. `-1` 종료는 실제 분기·값 근거를 공유하고, 임의의 0을 종료값으로 간주하지 않습니다. 포인터 버킷의 미조회 슬롯도 실제 초기 상태가 확인되는 경우에만 빈 루트로 표시해야 합니다.

## 4. 분리 배열의 필드 역할과 재해시 대응이 없음

```c
keys[p] = k;
values[p] = v;
flags[p] = 1;

// 새 저장소를 만든 뒤
for (int i = 0; i < old_capacity; i++)
    if (old_flags[i]) put(old_keys[i], old_values[i]);
```

03에서 `coindexed-record-candidate`는 같은 동적 인덱스로 묶인 배열들을 찾아냈습니다. 하지만 키·값·점유 역할은 없고, 재할당 전후는 독립된 저장 후보입니다. A의 활성 슬롯은 `[0:11, 1:1, 4:6]`, B는 `[0:11, 1:1, 5:16, 6:6]`입니다. 세 배열 모두 새 객체로 바뀌었고 기존 키·값은 보존됐습니다.

**공통 보완 방향:** 같은 인덱스 묶음을 유지한 채 검색 비교·반환·상태 조건에서 필드 역할을 추가합니다. 재해시는 이전 항목 READ → 호출 인자 → 새 항목 WRITE의 실제 출처로 대응시킵니다. 값이 우연히 같은 항목을 합치거나, 옛 저장소를 계속 살아 있는 것처럼 표시하지 않습니다. 자동으로 키 역할을 확인할 수 없으면 재배치/전달 관계만 보여주고 사용자 지정을 유지합니다.
