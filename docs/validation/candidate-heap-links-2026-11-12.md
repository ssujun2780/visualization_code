## 예측과 실제 결과

새 C 소스와 `.expected.json`은 실행 전에 저장했습니다. 출력뿐 아니라 실제 저장 원소, 순서, 관계와 사건 시점을 검사합니다.

```c
int precedes(const Item *a, const Item *b) {
    if (a->key != b->key) return a->key < b->key;
    return a->tie > b->tie;
}
/* insert에서 실제로 계산한 ancestor를 비교 인자에 전달 */
if (!precedes(store + cursor, store + ancestor)) break;
```

- `(4,1), (2,5), (3,7), (2,9)` 삽입 후 이진 힙의 물리 순서: `(2,9), (2,5), (3,7), (4,1)`. 0번 시작의 부모 연결은 `0→1, 0→2, 1→3`, 1번 시작은 각각 한 칸 이동합니다.
- 1번 시작 3진 힙의 물리 순서: `(2,9), (4,1), (3,7), (2,5)`, 연결은 `1→2, 1→3, 1→4`입니다. 이진 힙의 결과에 맞추지 않습니다.
- P 시점에는 최소 힙 조건 만족, 루트 키를 99로 바꾼 Q에서는 위반, 모두 꺼낸 뒤 사용 원소 수는 0입니다. 이는 정상 C 실행 중 자료구조 조건의 변화이며 실행 ERROR가 아닙니다.
- 주소 인자 `&store[i]`, 중첩 비교 도우미, 동적 할당에도 같은 원소·순서 조건을 검사했습니다. 기존 값 인자 비교자의 COPY 출처 검사도 유지했습니다.
- 같은 소스에서 입력에 따라 무관한 선행 할당을 추가해 객체 ID가 달라져도 선택이 복구됩니다. 실제 realloc 이후에도 새 후보로 연결되고, 이전 시점 조회는 원래 후보를 유지합니다.
- realloc 뒤 동점 비교 경로가 실행되지 않은 경우 선택은 복구하지만 `keyOrder:null`, `policyCoverage:partial-observed`, 힙 조건 unknown입니다. 이전 정책의 증거를 새 객체로 복사하지 않습니다.
- 독립 비교 함수와 사용하지 않은 `(i-1)/2` 식만으로 힙 원소를 만들지 않습니다. 역할을 바꾼 큐, 중복 후보, 달라진 비교 함수 선언, 발견 이전 시점은 임의로 연결하지 않습니다.

## 검증 중 발견·수정한 공통 문제

1. `&a[i]`는 별도 주소 CALC 없이 매개변수로 전달될 수 있었습니다. 실제 인자 WRITE와 호출 AST의 주소식을 연결했습니다.
2. 중첩 도우미에서는 상위/하위 프레임의 인자가 함께 추적되어 모호해졌습니다. 현재 필드 READ의 프레임에 속한 인자로 한정했습니다.
3. `T*`와 `const T*`를 서로 다른 물리 레코드로 취급하여 전체 동적 배열을 첫 필드 크기로 자르고 있었습니다. 바깥쪽 한정자만 물리 범위 비교에서 정규화했습니다.
4. 1번 시작 끝 커서의 사용 범위가 기존 0번 기반 관리 패턴에서 누락되었습니다. 실제 끝 원소 쓰기·증감의 출처로 보완했습니다.
5. 강화한 검증기가 COPY 원본 접근을 목적지로 검사했습니다. 접근 방향과 정확한 범위를 근거에 추가하여 두 쪽을 독립 검증합니다.
6. 기존 값 인자 비교의 COPY 호출자 프레임이 빠지고, 주소 인자 경유 시 내부 포인터의 부분 배열이 전체 인덱스 영역을 물려받는 회귀가 있었습니다. COPY의 실제 인덱스 증거를 연결하고, 선언 배열/실제 기준 주소를 확인했습니다. 기존 두 검사의 기준은 유지했습니다.
7. 재할당 뒤 관측 키 필드가 줄면 같은 비교 함수의 후보를 찾지 못했습니다. 관측 분기 목록과 후보 신원을 분리했습니다. 또한 미관측 동점 경로가 있는데 첫 키만으로 완전한 순서를 확정하던 부분을 수정했습니다. 동점 누락 검사를 완화하지 않았습니다.

새 기능에 맞춰 기존 `ir-structure-boundaries`의 포인터 비교 검사만 구현 전에 변경했습니다. 종전의 unknown 기대 대신 4개 실제 구성원·만족 상태·빈 최종 범위를 요구합니다. 그 외 기존 검사 실패는 기준을 바꾸지 않고 공통 추론기에서 수정했습니다.
