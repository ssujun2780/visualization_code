# No43 JSON 크기 조사

## 범위와 근거

사용자 요청은 원인 확인입니다. 중간언어 생성 모델·추론기·UI·저장 형식은 변경하지 않았습니다. 기존 `test-results/no43-diagnosis/observations.json`과 `recording.json`을 분석했습니다. C 코드를 재실행하거나 전체 예제를 검사하지 않았습니다.

기록의 소스 SHA-256은 현재 `examples/c/blind/No43.c`와 일치합니다: `ef592bca12503bc82a81e840e5526757042ee687988fede279b42b8921b4236c`.

적용 계약은 `presentation.md`의 모델/표현 경계, `c-model.md`의 실제 자료형·값·출처와 묶인 계산 보존입니다. 아래 공유 저장은 **진단 실험과 개선 제안**이며 제품 기능 구현이 아닙니다.

## 측정

단위 MB는 1,000,000바이트입니다. 저장된 두 파일 모두 `limited` 상태이며 추론 결과를 포함하지 않습니다(`trace.structures`는 빈 배열). 따라서 이 파일의 비대화는 직전 추론기 최적화와 다른 경로입니다.

| 기록 | 사건 수 | 현재 파일 | 같은 내용의 공백 없는 JSON | 자료형 표 참조 실험 |
| --- | ---: | ---: | ---: | ---: |
| 계측 관찰 | 26,571 | 41.19 MB | 22.40 MB | 15.46 MB |
| 공개 중간언어 | 11,872 | 84.39 MB | 38.53 MB | 22.85 MB |

공개 기록 84,391,050바이트에서 공백 없는 JSON은 38,534,456바이트입니다. **45,856,594바이트(54.3%)는 서식 공백**입니다. `scripts/shared/json-output.mjs`는 모든 배열·객체를 깊이에 따라 두 칸씩 들여써서 저장합니다. 사건 내부의 중첩 구조가 깊을수록 서식 크기도 커집니다. 스트리밍 저장은 거대한 문자열의 일시 할당을 피하지만 파일 자체를 축소하지는 않습니다.

공백을 제외한 공개 기록의 구성:

- `plan`: 12,318,541바이트. 이 중 명령 정의 9,896,107바이트이며, 명령의 `expression` 필드들만 5,939,825바이트입니다. 정적 계획은 실행 사건 수와 별도로 존재합니다.
- `trace`: 26,215,897바이트. 사건 배열은 23,531,125바이트입니다.
- 사건의 `inputs`: 5,612,179바이트, `value`: 5,561,484바이트, `steps`: 3,463,089바이트. 이 세 항목에는 자료형 설명이 포함되므로 아래 자료형 통계와 합산하면 안 됩니다.
- 사건의 `memoryState`는 총 11,299바이트입니다. 이 기록에서 큰 메모리 스냅샷이 주원인은 아닙니다.

## 반복되는 내용

공개 기록 전체에서 `cType` 객체는 **38,374회** 등장하지만, 직렬화 내용이 정확히 같은 것을 묶으면 **55종**입니다. 확장된 자료형 설명만 **16,342,757바이트**, 공백 없는 전체 데이터의 약 **42.4%**입니다. 여기에는 이름·부호·비트 폭·표시 정보와 포인터가 가리키는 구조체 필드 설명 등이 반복됩니다.

`ir-plan.mjs`의 `tree()`는 AST 표현식에 자료형·위치·자식 표현식을 붙이며 메모리에서는 캐시합니다. 일반 JSON 저장은 같은 객체의 참조를 공유하지 않으므로, 여러 명령에서 참조한 표현식/자료형도 매번 펼칩니다. `recorder.mjs`의 `semanticValue()`도 값에 자료형 객체를 붙입니다.

`ir-record.mjs`의 계산 묶음은 실제 관찰에서 `steps[].value`, `steps[].inputs`를 구성하고, 외부 입력들을 최상위 `inputs`로도 제공합니다. 계산은 한 사건이지만 내부 근거와 입력 정보의 JSON 표현은 중복될 수 있습니다.

실제 사건 `x10259`, No43의 178행 조건식은 공백 없이도 **17,226바이트**입니다. 계산 단계 4개, 입력 10개이며 같은 789바이트 포인터 자료형이 4회, 같은 695바이트 포인터 자료형이 4회 등장합니다. 같은 주소와 출처를 가진 983바이트 값 설명도 단계 입력과 전체 입력에 합계 4회 기록됩니다. 사건을 잘못 추가 실행한 증거가 아니라, 한 사건 안의 설명을 반복 직렬화한 경우입니다.

## 기록 한도와의 관계

저장된 진단은 사건 수 한도가 아닌 `trace-size-limit`입니다. 관찰 예산은 기본 **16,777,216바이트(16 MiB)**이며, 기록된 누적치는 16,776,858바이트입니다. `recorder.mjs`의 `event()`는 사건 추가 시점의 `JSON.stringify(event)` 크기를 누적합니다.

이 예산은 최종 파일 전체 크기 제한이 아닙니다. 계획·객체 목록·최종 변환·서식 공백은 따로 추가되고, 사건에는 추가 관찰 정보가 나중에 연결될 수도 있습니다. 따라서 저장 결과가 16 MiB보다 커지는 것을 막지 못합니다. 서식만 줄여서는 실행 중 관찰 예산에 도달하는 문제를 해결할 수 없습니다. 이 기록은 전체 실행이 완료된 결과가 아닙니다.

## 의미를 유지하는 개선 방향

1. 저장/전송의 기본 JSON은 공백 없이 쓰고, 사람이 읽는 출력에만 들여쓰기 옵션을 제공합니다. 관찰 사건·값·시점은 그대로입니다.
2. 정적 자료형·표현식·위치 설명을 공용 표에 저장하고 사건에서는 참조합니다. 같은 `cType.id`라도 const 등 내용이 다른 변형이 실제로 있으므로 ID 하나만으로 합치지 않습니다. 한 실행 안에서 설명 내용이 정확히 같은 경우만 공유해야 합니다.
3. 입력·결과·계산 단계가 반복해서 사용하는 **같은 값 기록**을 공용 기록으로 참조하도록 검토합니다. 서로 다른 시점의 값이나 같은 숫자인 다른 객체를 혼동하지 않으며, 단계 및 출처 연결은 보존합니다.
4. 내부 관찰 기록의 공유 방식과 바이트 예산도 함께 검토해야 합니다. 기록 한도 상향만으로 덮지 않고, 실제 저장/메모리 비용과 중복 설명 비용을 구분해야 합니다.

2번 중 `cType`만 공용 표로 바꾸는 진단 실험은 **22.85 MB**였으며, 원래 객체로 복원한 뒤 `assert.deepEqual`로 전체 내용의 동일성을 확인했습니다. 표현식·값 기록까지 공유하는 크기는 측정하지 않았습니다. 관찰 순서나 내용은 삭제하지 않았고, 실제 API/CLI에는 적용하지 않았습니다.

참고로 공백 없는 공개 기록을 gzip 압축하면 1,726,481바이트입니다. 이는 저장/전송 가능성을 보여주는 수치일 뿐이며, 압축을 푼 뒤의 파싱·메모리 비용이나 실행 중 관찰 예산을 해결했다는 뜻은 아닙니다.
