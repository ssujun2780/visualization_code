## 검사 방법

1. 코드에서 예상 출력, 특정 시점의 노드 식별자·연결 순서·종료 상태를 먼저 작성했습니다. `predictions.json`을 저장한 뒤 18개를 실행했습니다.
2. 발견한 원인을 구분하기 위한 19·20번도 별도 `control-predictions.json`을 작성한 뒤 실행했습니다. 기존 예상은 수정하지 않았습니다.
3. 노드는 값이 아니라 객체 식별자·부분 객체의 오프셋·크기로 비교했습니다. 여러 사례에서 데이터 값을 일부러 같게 두었습니다. 크기와 멤버 위치는 해당 실행의 컴파일러 자료형 정보에서 얻었습니다.
4. 정수 인덱스 방식은 **추론 결과에 실제로 존재하는 간선**을 예상 시작 인덱스에서 따라가 대조했습니다. 검사기가 따라갈 수 있었다는 사실과 추론기가 시작 변수에 연결된 순서 목록을 제공한다는 사실을 구분했습니다.
5. 비교 중 추론을 다시 적용할 때 입력 plan/trace가 바뀌지 않는지도 검사했습니다. 원본 실행 산출물은 교체하지 않았습니다. 관련 없는 예제 전체를 다시 실행하지 않았습니다.

## 보완점 1 — 미호출 함수가 실제 사용 증거처럼 추천에 영향을 줌

사례 15의 핵심입니다.

```c
int unused(N *p) {
    int s = 0;
    while (p) { s += p->v; p = p->n; }
    return s;
}
/* main: a[0]→a[1]→a[2]→a[3] 연결은 존재하지만, 아래에서는 값만 조회 */
N *table[3] = {a + 3, a + 1, a + 3};
for (int i = 0; i < 3; i++) s += table[i]->v;
```

실제 포인터 슬롯 후보 3개의 `traversalRoles`는 모두 빈 배열인데 `linked-list: supported`가 나옵니다. 미호출 `unused`만 제거한 19번에서는 배열·그래프 추천만 남습니다. 두 실행은 main의 동작·출력과 사건 수 73개가 같습니다.

저장된 연결이 목록 형태일 가능성 자체를 부정하는 검사는 아닙니다. **정적 코드상의 가능성, 실제 저장 형태, 실행에서 관찰한 순회 행동의 증거 수준이 섞인 것**이 문제입니다. 링크 후보 생성과 추천의 공통 경로에서 이 증거를 구분하고, 미호출 함수가 관찰된 사용 방식의 근거가 되지 않도록 해야 합니다.

## 보완점 2 — 포인터 배열 원소의 조회 범위를 배열 전체 크기로 계산

사례 20은 공유 꼬리 때문에 관련 후보가 함께 나온 것인지 구분하는 대조입니다.

```c
a[1].n = a;       /* 목록 0: [1,0] */
a[4].n = a + 3;   /* 목록 1: [4,3] */
N *roots[2] = {a + 1, a + 4};
```

각 목록 후보는 정확합니다. 하지만 `roots[1]`을 선택해도 `linked:pointer-slot:o5:0:debug:14`가 먼저 추천됩니다. 이 실행 환경에서 포인터는 4바이트, 배열은 8바이트인데 후보 범위가 `[0,8)`, `[4,12)`로 계산됩니다. 첫 후보가 두 번째 슬롯까지 덮고, 두 번째 범위는 배열 밖까지 늘어납니다.

`structure-storage.mjs`의 `structureStorageRanges`가 슬롯 너비에 소유 객체의 `cType.sizeBits`를 사용합니다. **실제 포인터 부분 객체의 자료형과 크기**를 사용하고, 저장소 경계 및 선택한 시작점과의 정확한 일치를 우선해야 합니다. 노드 내용이나 예제의 배열 길이로 보정하면 안 됩니다.

## 보완점 3 — 미기록 연결을 다른 추천 경로에서 완전한 목록으로 승격

사례 17은 잘못된 메모리를 읽지 않는 정상 코드입니다.

```c
a[0].v = 1; a[0].n = a + 1;
a[1].v = 1; /* a[1].n은 쓰지 않음 */
/* 순회 함수는 두 번째 값을 읽은 직후 break: a[1].n을 읽지 않음 */
```

연결 후보의 마지막은 `termination: unknown`이고 불완전 상태가 맞습니다. 그런데 저장소 참조 그래프에서 만들어진 `linked-list` 추천은 `status: supported`, `strength: 4`입니다.

`structure-presentation.mjs`의 `graphSnapshot`은 존재하는 간선의 상태만 검사합니다. 필요한 링크 슬롯 자체에 관측 간선이 없는 경우가 완전성 계산에서 빠집니다. **연결 대상 확인·NULL 확인·아직 미확인**을 노드/링크 역할마다 구분하고, 후보를 합치거나 추천 순위를 정할 때도 미확인 상태를 유지해야 합니다.

## 보완점 4 — 더미 노드의 물리적 존재와 데이터 구성원 수가 혼재

사례 05는 `box.nil`이 구조체에 포함된 경계 노드입니다.

```c
for (N *p = b->nil.n; p != &b->nil; p = p->n) s += p->v;
/* 목록을 비움 */
box.nil.n = &box.nil;
```

실제 `orders`는 데이터 2개에서 0개로 정확히 변합니다. 반면 `topology.nodeCount`와 추천의 `representedNodeCount`는 더미를 포함해 3개에서 1개로 변합니다. 빈 목록에 한 노드짜리 이진 트리/트리를 `supported`로 추천하기도 합니다.

`linked-views.mjs`는 경계 노드를 topology에 포함하지만 순서 목록에서는 제외하며, 추천은 topology의 개수를 사용합니다. **물리적 노드와 논리적 데이터 구성원·개수를 별도로 명시**해야 합니다. 더미를 메모리에서 지우는 수정이 아니라, 빈 목록 표현과 물리적 메모리 표현이 같은 필드를 다른 뜻으로 사용하지 않도록 하는 수정입니다.

## 보완점 5 — 원형 목록을 알아도 목록 표현으로 추천하지 않음

사례 04의 `[3,0,2]`와 사례 06의 자기 고리는 실제 데이터 머리를 포함한 순서와 `termination: cycle`이 정확합니다. 그러나 추천은 배열·그래프뿐입니다. 04의 마지막 링크를 NULL로 바꾸면 목록 추천이 다시 나타납니다.

공통 `shape` 함수가 모든 순환 topology에서 목록 추천 전에 종료합니다. **관측이 완전하고, 선택한 링크 역할에서 각 노드가 한 후속 노드로 이어지는 단순 고리**를 원형 목록 후보로 제공해야 합니다. 분기하는 순환 그래프나 미확인 연결까지 원형 목록으로 단정하면 안 됩니다.

## 보완점 6 — 인덱스 연결의 시작 변수·현재 도달 범위가 부족

사례 11입니다.

```c
links[6] = 2; links[2] = 5; int head = 6;
/* 현재 목록: 6→2→5→종료 */
links[6] = 5;
/* 현재 목록: 6→5→종료. 메모리에는 2→5도 여전히 존재 */
```

추론 간선에는 실제로 존재하는 `2→5`, `6→5`가 모두 남습니다. 이것은 맞습니다. 하지만 전역 그래프의 공유 자식 때문에 현재 `head`의 `[6,5]` 목록 추천까지 사라집니다. `head`를 직접 조회하면 후보도 없습니다.

10의 레코드 인덱스, 12의 표 형태, 13의 사용 목록/빈 슬롯 목록에서도 관리 정수 변수의 후보 조회가 비어 있습니다. 간선은 정확하며, 검사기가 예상 시작 인덱스에서 따라가면 순서도 맞습니다. **그 순서를 추론기가 시작 변수에 연결해 제공하는 기능은 부족합니다.**

정수 값의 전달 경로와 실제 인덱싱에서 확인한 배열 영역을 연결하고, 시점별 시작 변수에서 도달하는 구성원을 별도로 제공해야 합니다. 전역 그래프에는 분리된 노드의 실제 링크를 남기고, 사용 목록과 빈 슬롯 목록도 각각 유지해야 합니다. 같은 숫자가 있다는 이유만으로 배열과 관리 변수를 연결하면 안 됩니다.

## 보완점 7 — 연결 목록의 형태에서 큐의 동작 방식까지 이어지지 않음

사례 18의 삽입·제거는 다음과 같습니다.

```c
/* 삽입 */
p->n = 0;
if (*t) (*t)->n = p; else *h = p;
*t = p;
/* 제거 */
N *p = *h;
if (p) { *h = p->n; if (!*h) *t = 0; }
```

현재 `[1,4,0]→NULL`은 정확히 추론하지만 `queue` 추천은 없습니다. 현재 큐 동작 증명은 배열 기반 경로에 치우쳐 있습니다. 이것은 연결 자체의 오류가 아니라 **관찰한 삽입·제거 정책을 표현할 기능의 누락**입니다.

노드 식별자·수명과 머리/꼬리 및 링크 변경을 이용해 어느 끝에 삽입하고 제거했는지 공통 연산 증거로 요약해야 합니다. 그 증거로 FIFO/LIFO/양끝 조작을 구분해야 하며 함수명이나 데이터 값으로 판단하면 안 됩니다. 이번 실행에서 관찰한 FIFO를 프로그램의 모든 가능한 실행에 대한 증명으로 확대해서도 안 됩니다.

## 오류로 단정하지 않은 경우

08의 두 링크 역할을 합치면 이진 트리로도 해석할 수 있습니다. 두 필드의 독립적인 목록 순서는 보존됐고 목록 추천도 상위 5개 안에 있습니다. 이것은 의도 A를 무조건 B로 잘못 읽었다고 단정할 사례가 아닙니다. 역할별 근거와 대안 후보를 유지하고 사용자가 선택한 표현을 우선하는 기존 방향이 적절합니다.

또한 일반 목록을 퇴화한 트리로 표현할 수 있다는 사실 자체는 오류가 아닙니다. 이번 문제는 정확한 시작점·증거 수준·구성원 의미가 다른 후보를 잘못 연결하거나, 가능한 목록 표현을 누락한 부분입니다.
