# 배열 기반 스택·큐·덱: 다양한 구현과 반례 점검

2026-11-10. **모델·추론기·기존 검사는 수정하지 않았습니다.** 새 예제 16개와 원인 분리용 대조 예제 2개를 실행했습니다. 기존 예제 전체는 재실행하지 않았습니다.

## 방법과 결과 범위

1. C 코드와 예상 출력·관리 대상·사용 원소·논리 순서·추천해서는 안 되는 종류를 먼저 `predictions.json`에 저장했습니다.
2. API로 컴파일·실행한 실제 plan/trace/inference를 저장하고 출력 체크포인트에서 후보와 추천을 조회했습니다. 최종 종료 상태를 실행 중 상태로 오인하지 않도록 사건 시점별로 비교했습니다.
3. 원인을 좁히는 두 사례는 별도 `control-predictions.json`을 실행 전에 저장했습니다. 원래 예측·소스는 바꾸지 않았습니다.
4. 저장된 실행 기록으로 추론을 재조회했습니다. 결과 추출기의 복합 컨테이너 토큰 순서와 구조체 필드 타입 조회를 보완했지만, 예상값이나 제품 코드는 바꾸지 않았습니다. 재조회에는 C 재실행이 필요하지 않았습니다.

**18개 모두 예상 출력·종료 코드 0으로 완료했습니다.** 27개 시점/대상 조회, 중간언어 3,220사건이며 기록 공백과 설명되지 않은 관찰은 0개였습니다. 예상한 사용 위치의 실제 값도 모두 맞았습니다. 이는 추론의 정답 판정과 별개입니다. 아래 9개 보완점은 그대로 남아 있습니다.

작업 시작과 비교해 모델·계측·기존 검사 211개 파일의 SHA-256이 동일합니다. 저장된 plan/trace를 재추론해도 입력은 변하지 않았습니다.

## 우선 보완할 정확성 문제

### 1. 뒤의 동작으로 과거 후보까지 바뀜

13의 코드:

```c
put(&q,11); put(&q,22); put(&q,33);
int x = last(&q);
printf("S0 ...");             // 여기까지는 LIFO 근거
int y = first(&q);            // 이후 앞쪽 원소 제거
printf("S1 ...");
```

13에서는 S0·S1 모두 `roleCandidates=["active-prefix"]`, 추천은 배열뿐입니다. 17은 같은 함수 정의와 S0까지의 작업을 유지하고 뒤의 제거만 실행하지 않는데, S0에 스택을 추천합니다. 따라서 단순히 관찰 부족이라서 보류한 것이 아닙니다.

원인: `embedded-array-views.mjs`가 전체 실행의 `possibilities`와 `prefixPossibilities`에서 한 `chosen`을 선택하고, 그것으로 과거 states와 roleAlternatives도 만듭니다. 조회 시 근거 사건을 시간으로 걸러도 이미 삭제된 과거 LIFO 대안은 복구되지 않습니다.

공통 보완 방향: 후보 가설·성립 근거·반례를 시점별로 유지해야 합니다. 앞쪽 제거가 관찰된 시점부터 이전의 배타적 LIFO 판정을 철회하고, 이전 화면의 판정에는 영향을 주지 않아야 합니다.

### 2. 같은 배열의 독립 컨테이너를 합쳐 잘못된 비활성을 표시

14의 코드:

```c
int a[8], lo=0, hi=8;
void left(int x)  { a[lo++]=x; }
void right(int x) { a[--hi]=x; }
```

각각 두 번 넣고 한 번 꺼내면 실제로 `a[0]=11`, `a[7]=31`이 남습니다. 추론은 lo만 길이 역할로 선택하고 물리 배열 전체에 다음 상태를 부여합니다.

```text
logicalOrder = [0]
inactiveRanges = [{objectId: "o3", offset: 4, size: 28}]
unexplainedAccessExecutionIds = [x42, x55, x79]  // 오른쪽 작업
```

비활성 범위에는 사용 중인 a[7]도 들어갑니다. 오른쪽 절반을 조회해도 범위 겹침 때문에 같은 왼쪽 후보의 `stack`을 추천합니다. 그러므로 추천 이름만 보고 오른쪽도 성공이라고 판정해서는 안 됩니다. 원래 예상 인덱스 `[7]` 비교에서 실패합니다.

원인: 배열 전체를 하나의 문맥으로 만들고 관리 역할 하나를 선택합니다. 선택하지 않은 역할의 실제 작업은 unexplained로 남지만 비활성 계산과 조회 범위를 제한하지 못합니다.

공통 보완 방향: 물리 저장소와 논리 컨테이너를 분리하고, 각 관리 역할·작업 출처가 책임지는 범위를 유지해야 합니다. 한 후보에서 쓰지 않는 범위를 다른 후보도 쓰지 않는 것처럼 표시하면 안 됩니다. 물리 배열·실제 값은 그대로 유지합니다.

### 3. peek가 끝나지 않는 제거로 남음

05의 코드:

```c
int peek(void) { return h<t ? a[h] : -1; }  // h를 변경하지 않음
int take(void) { int x=a[h]; h=h+1; return x; }
```

실제 제거는 1회입니다. 두 peek의 READ `x59`, `x117`은 `missing-update`인 부분 dequeue로 분류되고, 이후에도 pending에 남습니다.

```text
front=1, back=4, activeRange=[1,4)
status="intermediate"
pendingAccessExecutionIds=["x59","x117"]
logicalOrder=null
```

18은 peek 호출만 리터럴로 대체하고 같은 저장·커서 갱신·출력을 유지합니다. 결과는 `supported`, 순서 `[1,2,3]`입니다.

원인: `queue-views.mjs`가 앞쪽 READ마다 제거 후보를 만들고, 연결할 커서 WRITE가 없으면 완료 시점 없는 pending 작업으로 둡니다.

공통 보완 방향: 읽기 관찰과 제거를 분리해야 합니다. 같은 커서 버전의 실제 증감·사용량 변경이 있을 때 제거로 연결하고, 정상 복귀한 단순 조회는 영구적인 미완료 작업으로 남기지 않아야 합니다. 기록이 도중에 끊긴 미완료 작업과는 구별해야 합니다.

## 표현 방식에 따른 누락

### 4. 개수가 아닌 마지막 인덱스를 놓침

02는 `z=-1; a[++z]=v; v=a[z--];`와 같은 규칙입니다. 현재 LIFO 판별은 삽입 전 개수 위치에 쓰고, 제거 후 개수 위치에서 읽는 형태를 기준으로 합니다. 마지막 인덱스 표현에서는 위치가 한 칸 다르므로 6개 작업이 모두 partial로 남습니다.

보완 방향: 실제 끝부분 접근과 갱신을 통해 기준 위치·증가 방향·오프셋을 추론해야 합니다. 이름이 top이라는 이유로 `+1`을 적용해서는 안 되며, 관찰로 확인한 표현에서만 길이를 유도해야 합니다.

### 5. 포인터 커서를 배열 관리 역할로 연결하지 못함

03은 short 배열을 할당하고 `*p=v; p++;`, `p--; return *p;`로 조작합니다. 실제 바이트·참조·읽기·쓰기는 기록되지만 `array-structure`가 생성되지 않습니다. 물리 배열은 유지됩니다.

보완 방향: `ArraySubscriptExpr` 중심 후보뿐 아니라 같은 할당을 가리키는 시작/현재/끝 포인터와 역참조도 연결해야 합니다. 원소 폭으로 정규화한 관측 오프셋을 역할 판단에 사용하며, 별도 할당의 우연히 가까운 주소를 합치면 안 됩니다.

### 6. 같은 이동을 memmove로 쓰면 FIFO를 놓침

06과 15는 입력·추가·제거·남은 값이 같습니다. 남은 원소를 당기는 방법만 다릅니다.

```c
// 06
--b->n;
memmove(b->a, b->a+1, b->n*sizeof b->a[0]);

// 15
for(unsigned i=1; i<b->n; i++) b->a[i-1]=b->a[i];
b->n--;
```

15는 큐로 인식하지만 06은 배열로만 남습니다. 06의 중간언어에는 이미 `x78 WRITE/copy`, 동일 객체의 `sourceOffset=4`, `sourceSize=8`, 목적지 offset 0·size 8, 원래 삽입 WRITE 출처 `[x36,x53]`가 있습니다. 복사 사실이 중간언어에서 빠진 문제가 아닙니다.

원인: 이동 판별이 원소 단위 READ/WRITE 쌍을 모아 개수와 목적지 집합을 확인하는 경로에 치우쳐 있습니다.

보완 방향: 두 표현을 동일한 범위 이동 관계로 해석하되, 실제 중간언어에 없던 READ/WRITE를 추가해서는 안 됩니다. 겹치는 복사의 원본 시점과 원소별 출처를 보존해야 합니다. 값이 같은 7이라는 이유로 두 원소를 합쳐서는 안 됩니다.

### 7. count 없는 원형 큐를 놓침

07의 head+count는 감김·비움·재사용 모두 맞습니다. 08의 head/tail은 다음처럼 경계에서 돌아오고 한 칸을 비웁니다.

```c
unsigned next(unsigned i) { i++; if(i==5) i=0; return i; }
unsigned k=next(b->t);
if(k==b->h) return 0;
b->a[b->t]=x; b->t=k;
```

실제 head 2·tail 1 상태의 순서는 `[2,3,4,0]`이고, 비운 뒤 둘 다 1입니다. 추론은 두 상태 모두 미확정입니다.

보완 방향: 순환 커서의 실제 전진·되감김과 빈 상태/포화 방지 비교를 함께 연결해야 합니다. `%` 문법만 찾거나 head==tail을 모든 구현에서 빈 상태로 가정하면 안 됩니다. 별도 count·full 표지를 쓰는 방식과 한 칸을 비우는 방식을 구분할 근거가 필요합니다.

### 8. 이동식 덱의 네 가지 끝부분 작업을 합성하지 못함

09의 원형 덱은 인식하지만 10의 반복문 이동식 덱은 active-prefix만 남습니다. 최종 길이 2·순서 `[0,1]`·값 `[5,10]`은 맞습니다. 기대한 삽입 4회·제거 2회 중 마지막 앞쪽 제거가 작업 근거에 포함되지 않습니다.

보완 방향: 앞/뒤 삽입·앞/뒤 제거의 관계를 공통 작업으로 조합해야 합니다. 현재 이동식 FIFO와 LIFO의 일부 조합에 있는 판정을 네 가지 끝부분 작업으로 확장하고, 실제 원소 이동도 근거로 보존해야 합니다.

### 9. 종류를 모른다는 이유로 확인 가능한 사용 범위도 보류

11은 `if(n<5) a[n++]=x;`로 3개를 넣고 n 직전까지 순회합니다. pop 함수는 정의만 있고 실행하지 않습니다. 스택·큐로 확정하지 않은 것은 맞습니다. 하지만 길이와 사용 범위 `[0,1,2]`도 null입니다.

원인: 내장 배열의 접두 범위 선택에는 여전히 삽입·제거 양쪽 근거를 요구하는 경로가 있습니다. 직전 보완의 별도 변수/동적 관리 연결과 달리, 이 형태의 내장 배열은 사용 범위가 확정되지 않습니다.

보완 방향: 실제 쓰기 범위와 관리 값 증가·경계 관계로 사용 범위를 판정하고, LIFO/FIFO 여부는 별도로 보류해야 합니다. 읽어 본 곳만 사용 중이라고 표시하는 단순 순회 반례와도 구분해야 합니다.

## 정상 처리와 중복 값의 확인

- 일반 개수 스택, realloc 스택, head+count 원형 큐, 원형 덱은 기대 순서와 추천이 맞았습니다.
- 삽입만 한 시점·미실행 pop 함수·서로 다른 배열의 복사에서는 스택/큐/덱을 잘못 확정하지 않았습니다. 다만 11의 범위 누락은 별도 문제입니다.
- 두 스택으로 만든 큐는 내부 스택과 합성 큐를 함께 보존했습니다. 같은 값 7 두 개의 삽입 토큰은 `x25`, `x51`로 구분됩니다. 첫 제거 후 순서는 `[x51,x77]`, 두 번째 제거와 후속 삽입 후에는 `[x77,x241]`이며 실제 값은 `[9,8]`입니다. 숫자만 비교해서 FIFO를 통과시킨 것이 아닙니다.
