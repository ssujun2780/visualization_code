## A. 구조체 반환의 공유 저장소를 재생기가 거부함

같은 값·출력을 내는 다음 반환 형태에서 결과가 갈립니다.

```c
typedef struct { int first, second; } Pair;
static Pair make(int x) {
    Pair temporary = {x, x + 4};
    return temporary;
}
// 대조: return (Pair){x, x + 4};
```

- 21_named_return: 출력 7 11, 정상 종료, 27사건. 재생은 “독립 저장소가 없는 별칭 객체는 이 화면에서 지원하지 않습니다.”
- 22_literal_return: 동일 출력, 26사건, 재생 성공.
- 긴 CSR 다익스트라도 동일 원인. x2732 SPACE/object.begin의 o284(answer)에 storageAlias.rootObjectId=o281, offset 0, size 8이 기록되고 x2734 WRITE/copy도 존재합니다.

원인은 **src/animation/playback.js:59의 storageAlias 일괄 거부**입니다. 생성 기록 누락이 아닙니다. 공통 수정은 소스 이름·수명과 실제 저장소를 분리하고 별칭의 rootObjectId+offset을 같은 메모리에 연결하는 것입니다. 지역 이름 종료가 호출자 저장소 종료가 되어서는 안 됩니다. 사건 삭제나 가짜 별도 할당은 해결책이 아닙니다.

이 사례의 작업 분석에도 unobserved-memory-producer 58건이 있습니다. v2/common.mjs의 storage()와 provenance 범위 비교가 별칭 ID를 다른 저장소로 취급하는 경로를 함께 보완해야 합니다. 숫자 주소의 우연한 일치가 아니라 기록된 별칭·수명을 사용해야 합니다.

## B. 포인터 관계 근거의 NaN이 부가 분석 전체를 실패시킴

## C. 순회 인덱스를 큐의 앞·뒤 변수로 오인하고 확정 추천함

```c
for (int i=0; i<20; i++) dist[i]=-1;
/* BFS의 임의 위치 dist 읽기·갱신 */
for (int i=0; i<20; i++) printf("%d ", dist[i]);
```

BFS에서 실제 queue뿐 아니라 **dist도 queue로 자동 선택**됩니다. dist 후보의 back은 초기화 루프 i(o11), front는 출력 루프의 다른 i(o248)입니다. assessment는 partial이고 미설명 접근은 82건인데, 추천은 queue/supported/1순위입니다. 다익스트라 dist와 LCS 행 포인터 표에서도 같은 계열이 나왔습니다.

queue-views.mjs에서 끝점 접근/갱신 조합이 서로 다른 수명의 순회 변수까지 연결합니다. structure-presentation.mjs의 queue 분기는 enqueue/dequeue 예가 있고 contradicted 작업이 없으면 partial·미설명 접근을 무시합니다.

공통 수정: 관리 역할의 수명·소유 범위·구간 제어와 삽입/제거 출처를 함께 판단합니다. 독립 초기화/출력 순회는 배열 순회로 남기고, 불완전성을 추천까지 보존합니다. 변수명이나 특정 문법으로 큐를 식별하지 않아야 하며 함수로 전달한 정상 커서도 유지해야 합니다.

## F. 관계 발견과 자동 선택·세부 종류 판별의 차이

- 부모 포인터 BST: 자식 역할의 **binary-tree/tree 후보는 이미 3·4순위로 발견**됩니다. 기본값은 부모 역참조까지 포함한 graph(9노드·16간선). 트리를 전혀 못 찾은 것이 아닙니다. 주 관계/역참조의 추천 우선순위와 세부 BST 판별은 보완 여지가 있습니다.
- 희소 트라이: **6노드·5간선**과 tree-or-forest 위상은 찾았지만 종료/활성 범위는 partial이고 기본값은 array입니다. 문자 슬롯 역할·종료값·미사용 용량과 트라이 종류를 충분히 확정하지 못했습니다.
- 분리 배열 자유 목록: 활성 7노드·6간선의 linked-list가 나왔습니다. 전체 용량을 모두 활성 구성원으로 삼지 않았습니다.
- LRU: 해시 체인과 최신 사용 순서가 혼재한 전체 graph는 얻었습니다. 이것을 LRU 의도까지 판별했다고 계산하지 않았습니다.

이들은 확정 오류 A~E와 구분한 **추론 품질·자동 선택 보완 후보**입니다. 관계/조건을 조합하고 사용자 선택을 유지해야 하며 예제 이름을 해석 규칙에 넣으면 안 됩니다.

최고 RSS 약 855.5MiB는 **컴파일러 런타임·원시 관찰·직렬화/압축 임시 객체·여러 단계 결과를 보유한 검사 프로세스 전체** 수치입니다. 브라우저나 추론기 단독 메모리가 아닙니다. 전체 수치는 timings.md, 순수 단계 CPU 근거는 profile-*-summary.json에 있습니다.

## J. VLA 보조 계산의 진단을 실제 누락과 구분해야 함

int grid[n][n]의 m25는 LLVM의 mul nuw i32 n,n → alloca 개수 계산입니다. 계획에는 no reliable source expression으로 남지만 irGaps는 비어 있고 실제 배열 접근·출력·재생은 정상입니다.

독립적인 사용자 산술식이 아니라 공간 크기를 구하는 보조 계산이므로 새 CALC를 무조건 추가해야 한다고 판단하지 않았습니다. 공간 크기 근거로 분류하고 실제 연결 실패와 구별할 진단 보완 후보입니다. 기존 검사 불일치는 그대로 남겼습니다.

## 추가 관찰·다음 순서

qsort 콜백의 첫 전달선 표본 하나는 약 167ms였습니다. 경로 누락은 없었으나 초기 지연 후보입니다. 반복 측정·실제 브라우저 FPS 검사가 없어 지속 저하로 단정하지 않았습니다.

버블 32와 LRU 두 사례는 기존 추론 상태 한도로 일부 이력을 생략했습니다. 진단은 유지되며 원본 C 실행 사건은 잘리지 않았습니다. 한도 변경·기록 삭제는 하지 않았습니다.

수정 순서는 **A/B 재생·분석 실패 → C/D/E 추천·중복·시점 → G/H/I 공통 성능 → F/J 품질·진단**을 권합니다. 사전 예상값·반례를 유지하며 해당 경로만 재검사해야 합니다. 이 문서는 발견 보고서이며 수정 구현 완료를 뜻하지 않습니다.
