# No43 준비 단계의 불필요한 관계 계산 제거

## 범위와 기준

앞선 [시간 초과 수정](no43-preparation-fix-2026-11-13.md) 후에도 API 경로의 준비 Worker가 144.72초 걸렸습니다. 이번에는 남은 준비 비용을 측정한 뒤 공통 소비 경로만 변경했습니다.

읽은 계약: `presentation.md` 책임 경계, `prepared-scene.md` PS-01~04, `inference-model.md` 읽기 전용 소비자, `structure-presentation-policy.md` 적용 규칙, `animation.md`·`visualization.md`·`ui.md`의 현재 준비/재생 경계입니다. 원본 실행·추론 결과·선택 정책·표현 제한·180초 제한을 유지합니다.

고정 입력은 앞서 정상 완료한 No43의 plan/trace와 최종 499개 추론 후보입니다. 비교 기준은 최종 stdout이나 몇 개 노드만이 아니라 **준비 결과 전체의 strict deep equality**입니다. 다른 예제도 기존 계약 검사로 확인하며 검사 기대값을 바꾸지 않습니다.

## 원인

`createStructureViewQuery().project()`는 전체 저장 그래프를 선택한 경우에도 먼저 `queryStructureRelations()`로 일반 후보 관계를 조회했습니다. 수동 그래프 선택에서 특정 후보 ID가 없으면 모든 후보를 훑으며 저장 범위·시점 상태를 구하고 결과를 복제했습니다. 이어서 `storageReferenceView()`의 결과가 있으면 앞의 결과를 통째로 버렸습니다. 고정 표현의 여러 객체·시점마다 같은 낭비가 반복됐습니다.

준비 단계 20초 CPU 표본에서는 저장 범위·상태 검색, 일반 관계 조회와 `structuredClone`이 큰 비중을 차지했습니다. 저장 그래프 자체 조회 외에, 실제 결과에 사용되지 않는 계산이 주요 비용이었습니다.

웹과 같은 세션 API 미들웨어 요청·Accept 헤더·JSON 직렬화/복원을 거쳐 제품 `prepared-worker.js`로 다시 확인했습니다.

## 근거와 제한

`test-results/no43-preparation-optimize/`에 `cpu.json`, `baseline-report.json`, `baseline.json`, `after-queries.json`, `equality.json`, 실제 API 미들웨어와 제품 Worker 연결 재현 스크립트를 보관합니다. 기존 산출물과 원본 C 예제는 변경하지 않았습니다.

API 측정은 `api-worker-report.json`, 전후 API 결과 비교는 `api-equality.json`입니다. 로컬 HTTP 소켓 대신 미들웨어에 같은 요청을 직접 전달했으며, Firefox 네트워크·화면 조작을 측정한 결과는 아닙니다.

제품 Vite 빌드도 통과했습니다. 기존 큰 청크 경고는 유지됩니다.

실제 화면 가독성·Firefox 시간은 이번 검증 범위에 포함되지 않습니다. 추론 후보/이력 한도 경고를 지우거나 준비를 생략해서 시간을 줄인 것이 아닙니다.
