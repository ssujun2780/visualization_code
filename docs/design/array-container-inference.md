# 배열 컨테이너의 관측 기반 추론

2026-11-10. 중간언어 생성 이후에 실행되는 부가 추론 규칙입니다. 원본 AST·중간언어·객체·실행 사건은 읽기 전용이며, 화면용 후보와 근거만 만듭니다.

## 저장소, 사용 범위, 제거 정책의 구분

- AST의 배열 크기와 실행 중 확인한 할당·포인터 대상을 물리 저장소로 삼습니다.
- 어떤 관리 슬롯이 어떤 원소의 주소 계산에 실제 사용되었는지 연결합니다. 변수 이름이나 값의 우연한 일치로 역할을 부여하지 않습니다.
- 쓰기와 관리 값 변경, 경계 비교 또는 끝 원소 접근은 사용 범위의 근거입니다. 제거 작업을 실행하지 않아도 확인 가능한 범위는 표시합니다.
- LIFO/FIFO/양끝 사용은 별도의 작업 근거가 필요합니다. 정의만 된 pop 함수나 `% capacity`만으로 종류를 확정하지 않습니다.
- 반환·조회만 하고 관리 위치를 바꾸지 않은 읽기는 제거와 구별합니다. 누락된 출처 연결이 있거나 호출이 끝나지 않은 관찰은 조회 완료로 간주하지 않습니다.

### 구조체 필드의 저장 경계

일반 배열 보기와 포인터 기반 컨테이너는 `array-storage-extent.mjs`의 같은 범위 판정을 사용합니다. 객체 식별자·오프셋과 컴파일러의 필드 타입·크기로 실제 대상 범위를 제한합니다. `N **p = &node->next; *p = value;`처럼 단일 필드의 주소를 얻고 역참조하는 것만으로 배열을 생성하지 않습니다. 할당의 남은 바이트를 모두 필드의 배열 용량으로 사용하지 않습니다.

중첩 구조체와 typedef·const를 거친 필드도 컴파일러 타입 관계로 확인합니다. 실제 배열 필드 `N *items[1]`은 한 칸 배열로 유지하며, 뒤쪽 필드·패딩까지 확장하지 않습니다. 포인터가 다른 대상에 다시 연결되면 새 대상의 범위를 따로 판정합니다. 단일 레코드와 실제 레코드 배열도 기존 선언·인덱스 접근 근거로 구별합니다.

이는 타입과 관측된 저장 범위를 확인하는 규칙입니다. 이름·특정 주소·예제 번호로 예외를 만들거나 포인터 역참조를 일괄 제외하지 않습니다. [범위 판정 수정과 검증](../validation/scalar-field-array-fix-2026-11-11.md)을 참고하십시오.

## 시간별 역할과 공유 저장소

`array-structure.roleAlternatives`는 실행 전체에서 수집한 가설 목록입니다. 현재 시점의 판단에는 반드시 `states[].roleAssessments`와 `selectedRole`을 사용합니다. 지원·모순 근거는 해당 상태 이전에 완료된 사건으로 제한합니다. 나중에 앞쪽 제거를 실행했다고 그 이전의 스택 근거를 지우지 않습니다.

관리 슬롯이 다른 독립 컨테이너들은 같은 배열을 사용해도 별도 후보가 됩니다. 이 경우 `queryScoped: true`와 상태의 `scopeRanges`로 클릭 대상의 후보를 구분합니다. 비활성 범위는 해당 컨테이너가 사용한 슬롯에 한정합니다. 다른 컨테이너의 원소나 아직 소속을 확인하지 못한 공간을 비활성으로 덮지 않습니다.

`roles`와 최종 `roleCandidates`만 보고 과거 시점의 순서를 재구성하면 안 됩니다. 위치·값은 원본 저장소에 두고, 시점별 `logicalOrder`를 표현상의 순서로 사용합니다.

## 끝부분 작업의 공통화

| 표현 차이 | 공통 근거 |
| --- | --- |
| 개수, 마지막 인덱스, 역방향 커서 | 관측된 초기 좌표, 삽입/제거 시 증감 방향, 실제 접근 위치의 차이 |
| 포인터 커서 | 실제 대상 객체·바이트 오프셋과 원소 크기. 수치 주소의 유사성은 사용하지 않음 |
| 전위·후위 및 함수 없는 인라인 코드 | 각 작업의 주소 계산에 쓰인 커서 읽기 버전을 해당 변경에 연결 |
| 반복문으로 이동 | READ→WRITE의 값 출처와 원소별 이동 방향 |
| `memmove` 등 범위 복사 | 기존 WRITE/copy의 원본·대상 범위와 크기. 가짜 READ 사건을 추가하지 않음 |
| 이동식 덱 | 앞/뒤 삽입과 앞/뒤 제거를 합성. 다른 끝을 사용한 근거가 생기기 전에는 덱으로 승격하지 않음 |
| 개수 없는 원형 큐 | head/tail의 실제 전진·되감김, 다음 tail과 head의 포화 방지 비교, 실제 삽입·제거 |

범위 복사의 원소 관계에는 `kind: observed-range-copy`와 `copyExecutionId`를 기록합니다. 개별 복사에는 실제 `readExecutionId`·`writeExecutionId`를 기록합니다. 둘 다 기존 사건의 해석이며 중간언어 사건 수를 늘리지 않습니다.

`logicalOrder.direction`은 `1` 또는 `-1`입니다. 배열 끝에서 자라는 스택도 같은 형식으로 나타냅니다. `ir-schema.mjs`에서는 **자료구조 부가 정보 검사 함수인 `validateStructureTrace`만** 이 형식과 범위·시점 근거를 검사하도록 확장했습니다. 실행 중간언어의 생성·검사 규칙은 변경하지 않았습니다.

## 모호성과 한계

초기 커서가 2라는 사실만으로는 이미 원소 두 개가 있는 개수인지, 2부터 시작하는 빈 커서인지 결정할 수 없습니다. 두 해석이 모두 맞으면 순서를 보류합니다. 실제 빈 경계와의 비교가 있으면 그 근거 이후에 좌표 해석을 선택할 수 있습니다.

한 칸을 비우는 원형 큐와 full 표지가 있는 원형 큐는 다릅니다. 후자는 별도 근거 없이 head==tail을 빈 상태로 해석하지 않습니다. 이번 보완은 full 표지를 쓰는 모든 구현의 의미까지 자동 확정하지 않습니다.

일반적인 사용자 지정 우선·추천 상위 다섯 개 규칙은 유지합니다. 추론의 미확정·모순 상태는 C 실행 오류를 새로 만들거나 정상 실행 기록을 수정하지 않습니다.
